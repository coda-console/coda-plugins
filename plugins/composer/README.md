# 输入框模式

`@coda-console/composer` 把输入框的五种模式放在同一个插件里，插件 ID 为 `composer`；另带入口流程「开工」（`kickoff`）、两个开发流程：监督开发（`develop`，一个需求一条泳道）与需求交付（`deliver`），以及监督开发里主 Agent 往泳道提改动用的「泳道 PR」（`lane-pr`）。开发流程由你在会话里开启，或由 Agent 发起「开工」后你在开工卡上确认。

| 模式 | 入口 | 用途 |
| --- | --- | --- |
| 交接到新会话 | `/handoff` | 新会话承接当前上下文，共享工作目录；原会话保留，可继续使用。 |
| 子会话 | `/subagent` | 从任意会话启动子会话，承接近期上下文并沿用工作目录；可选完成后回报父会话或你。 |
| 执行命令 | `!` | 在会话工作目录执行命令，命令与结果作为消息发给 Agent；也可在新任务输入框使用。 |
| Ultra | `/ultra` | 主 Agent 定任务、做决定、审查，不改代码的调研与核实按任务交给名单里的执行者；也可在新任务输入框使用。 |
| 循环 | `/loop` | 按周期把同一句话再发给 Agent，每轮做完才开始计时，7 天后自动结束；仅用于已有会话。 |

五个模式可同时开启，模式 ID 不变。Ultra 开启时，从这个输入框创建的新会话（包括子会话、交接和新任务）继承 Ultra 及当前子 Agent 名单，各自独立保留模式；关闭来源的 Ultra 不会关闭已创建会话的 Ultra。工具栏始终选择输入框自己的执行者；交接与子会话的参数另有可选 Agent，留空沿用输入框执行者。子会话也能创建自己的子会话。

3.0.0 按 [Coda #2063 的接口约定](https://github.com/coda-console/coda/issues/2063) 改为 `submissions` 协议参与者，依赖该 issue 第 2 步的后端支持，以及 [Coda #2085](https://github.com/coda-console/coda/pull/2085) 的新会话模式继承与实际投递计数，不能用于旧版回调宿主。交接、子会话和循环声明 `once: true`，发出的一条被收下后退出该模式；Ultra 保持开启，执行命令的触发词仍是 `!`。

4.0.0 跟随 [Coda #2176](https://github.com/coda-console/coda/issues/2176) 的协议命名：输入的观察与发出的一条的参与者改用 `coda/composer@1`、`coda/submission@1`，需要支持协议名的新版 Coda，不能用于旧版。本插件不定义也不实现协议，只作为参与者登记补充。同一版本还包含 main 上 3.10.0、3.10.1 的改动（[#197](https://github.com/coda-console/coda-plugins/pull/197)、[#199](https://github.com/coda-console/coda-plugins/pull/199)）：develop 的合并前检查挪到批准卡之前，批准、放行后直接合并；合并冲突退回执行者；流程定义去掉了 `coda:handback`，跟上 Coda 的「流程任务每层一轮」。

6.0.0 按 [Coda #2504](https://github.com/coda-console/coda/issues/2504) 把监督开发改成一个需求一条泳道：主 Agent 用新流程「泳道 PR」（`lane-pr`）把改动一块块合进泳道，需求做完才开泳道进目标分支的 PR，用户只批一次，用合并提交（不再 squash）进目标分支；收尾的失败和「暂不合并」回到「需求进行中」。与旧版输入不兼容：`develop` 去掉 `task`、`executor`、`executor2`、`reviewerOnce`，改收 `goal`，`reviewer`、`reviewer2` 改为整体评审者；`kickoff` 去掉 `executor`、`executor2`、`reviewerOnce`，把目标作为 `goal` 传给 `develop`；需求交付的成员改为各仓库的需求运行（发起 `develop` 时传 `title`、`goal`）。执行者和每次交付的评审者挪到 `lane-pr` 上，由主 Agent 每个泳道 PR 自己定。

插件只返回补充，不改正文、附件、引用或输入框的执行者。多个模式的补充由 Coda 合并，`tell` 是字符串数组，按列表追加后随这条发送到每个收到它的会话；只要有一项 `divert: true` 就不发给默认去向，各模式追加的去向仍分别执行。

| 模式 | 发出的一条的补充 |
| --- | --- |
| 交接 | `divert: true`，追加 `thread` 去向，带 `handoffSource`、可选 `agent`、`open: true` |
| 子会话 | `divert: true`，追加 `thread` 去向，带 `handoffSource`、`parentThreadId`、`replyTo`、可选 `agent`、`open: true` |
| Ultra | 创建新会话（交接、子会话、默认去向为新会话）时返回完整开启说明；已有会话里，仅当状态标记要给完整说明（首次、改名单、压缩后）时返回，其余返回 `null`；每轮提醒由 watch 给（见「Ultra 用法」） |
| 循环 | `divert: true`，追加 `loop` 去向，带 `thread`、`every` |
| `!` | `divert: true`，会话中追加 `message` 去向，带 `thread`、`run: true`；新任务中追加 `thread` 去向，带 `run: true`、`open: true` |

新会话去向明确跳转，客户端按每项 `open` 执行。Coda 将非一次性、非触发式且适用于会话的模式和参数写入新会话输入框；各会话只为自己实际收到的模式消息计数，转发到新会话不增加来源的 `sent`。空 Agent 不写入目标，交由 Coda 沿用 `spec.agent`（包括 settings）。

## 循环用法

在已有会话的输入框里打 `/loop`，填写每轮要做的事，选择周期后点「开始循环」。周期默认 30 分钟，可选 5 分钟、10 分钟、15 分钟、30 分钟、1 小时、2 小时、3 小时、6 小时、12 小时或 1 天。

这条消息就是第 1 轮；Coda 收下后创建循环，输入框随即退出循环模式。每轮做完才开始计算下一个周期，不叠着跑；7 天后自动结束，也可提前停止，归档会话同样结束循环。计时与重发由 Coda 后端负责，会话进程被回收后仍会按时恢复。

循环的计时行为沿用 [Coda #2051](https://github.com/coda-console/coda/pull/2051)，3.0.0 通过上述 `loop` 去向提交。

## Ultra 模板设置改名

Ultra 的模板设置由 `ultra.templates` 改为 **`composer.templates`**，模板的数据结构不变。清单的预设只引用新设置名，由 Coda 按输入框所在目录读取。
旧 Ultra 包暂时保留，旧设置迁移和卸载旧插件由 [Coda issue #2050](https://github.com/coda-console/coda/issues/2050) 的第 4 步处理，本插件不自行迁移。

## Ultra 用法

在会话或新任务输入框打 `/ultra`，点模式条选择执行者名单；点 × 退出。单独开启时消息照常发给当前会话，与其他模式一起开启时按各模式的去向发送。
Ultra 只管派活：主 Agent 定任务、处理困难决策、审查别人交回的东西；不改代码的调研、排查和核实用 Coda 的 `spawn` 交给名单里的执行者，按任务挑。
它不规定代码怎么改、走不走开发流程：开发流程由你在会话里开启，或由 Agent 发起「开工」后你在开工卡上确认（见下文），它的规则写在交给主 Agent 的任务里。

`composer.templates` 是执行者模板，一行「模板名、Agent、什么时候派给它」。同一模板名的行是一组，进入时填第一组；默认没有模板。
Ultra 参数仍保存为 `subagents`，预设引用 `{ "from": "composer.templates", "by": "template" }`，选择预设只填入名单一次，之后可修改。
派活时任务书要自成一体：目标与它服务的决定、已知或已排除的、范围与不要碰的、去哪里找、交回什么（先结论，再来源和实际证据）。
结果不好时按原因处理：任务书漏了的，补写后发回同一会话；只有说法没有证据的，向同一会话要证据；任务书清楚但结果不对的，换名单里的另一项；会话中断或工具失败的，重试；不要自己悄悄重做。
名单管的范围：Coda `spawn`，泳道 PR（`lane-pr`）的 `executor`、`executor2`、`reviewer`、`reviewer2`、`reviewerOnce`，以及开工（`kickoff`）与监督开发（`develop`）的整体评审者 `reviewer`、`reviewer2`，都按任务从名单选，传 `agent`、`model`、`effort`、`mode`、`options`；只有名单为空或没有条目覆盖这项工作时，才用当前会话的 Agent 和模型。提示只讲从名单选谁，不讲开发流程怎么走。

会话输入框开着 Ultra 时，这个会话的每一轮开头都带 Ultra 提醒，不论这一轮由用户消息、流程结果还是卡片叫醒。
默认是短提醒：一两句要点（主 Agent 定任务、做决定、审查；不改代码的调研与核实交给 `spawn`；不用原生子 Agent；并发满了就等），加上名单和名单的范围；名单为空时写用自己的 Agent。
下列情况改给完整说明，之后回到短提醒：Ultra 首次生效、名单改过、压缩（Ultra 的 `sent` 由大于 0 变 0）。
输入框的变化只更新插件内存里的状态（名单、`sent`、是否要给完整说明），不 `tell`；提醒只在两个时点给：

- 一轮结束（`coda.watch('threads')` 里 `turn` 由非空变 `null`）：要给完整说明的给完整说明，否则给短提醒，用 `coda.tell` 追加成下一轮开头读到的消息。
- 用户在已有会话里发消息（`coda/submission@1` 参与者）：要给完整说明的随这条消息带出并清掉标记，否则返回 `null`。创建新会话时照旧返回完整说明（新会话还没有上一轮）。

所以改名单在下一次发消息或下一轮结束时生效：空闲时连着改几次只给一份最新名单的完整说明；改了名单没发消息、下一轮又由流程叫醒时，这一轮读到的仍是上一轮结束时排好的短提醒，这一轮结束后才给新名单的完整说明。偶尔一轮里同时有短提醒和完整说明属正常。
怎么认新会话：带着 Ultra 新建的会话，输入框与第一条在同一个事务里写成 `sent=1`，第一条已带完整说明，第一轮结束给短提醒；刚进入 Ultra 时 `sent=0`，给完整说明；插件重启后重放的输入框当作首次，给完整说明（重启后会多给一次）。
新任务输入框（`new:…`）本身不提醒，它创建的会话照上面处理；未开 Ultra 的会话不提醒。状态只放内存。

6.2.0 起 Ultra 每轮提醒（原来按用户发出的消息每 10 条一次，长程任务里会话多半被流程结果叫醒，计数不动，压缩后名单也丢了），提醒带名单，名单也管泳道 PR 的执行者与评审者、开工与监督开发的整体评审者。
并发已满就等名额；spawn 不可用就报告阻塞，不改用原生子 Agent。用户的明确指令优先。
5.0.0 起 Ultra 不再要求「所有代码修改都通过 develop」，也不再讲 develop、deliver 的用法；两个流程改为由你在会话里开启，或由 Agent 发起「开工」后你在开工卡上确认，develop 的执行者从 `agent`、`model`、`effort`、`mode` 四个参数换成一个 `executor`（Coda #2303）。需要支持流程参数 `agent` 类型（协议 3.5.0，Coda #2332）、`coda:wake` 与 `note="required"` 的 Coda，不能用于旧版。

插件声明 `activationEvents: ["onStartupFinished"]`，重启后通过 `coda.watch('threads', …)` 与 `coda.watch('coda/composer@1', …)` 恢复观察。
Ultra 消失时，若这个会话收到过说明（submission 投递过或 watch 告诉过；重启后不知道时按 `sent > 0` 判断）就用 `coda.tell` 告知关闭一次，恢复通常的执行与委派规则，此后不再提醒；没收到过就不说。
名单连同说明超过 Coda 单次告诉 Agent 的 4000 字上限时，缩短名单再发。这些分工是提示词约束，不在运行时禁用工具。

## 开工

Agent 要把改动合进默认分支时，一个需求开一次「开工」（`kickoff`），由你在卡上决定走哪条开发流程。它不声明 `coda:kind`：只是入口，不是一种开发实现。
需求是你想一起验收、一起上线的一件事；只有必须先上线才能往下做时（别人等着用，或要先部署才能验证），Agent 才把它拆成几个需求、依次开工。小修走简易开发。
Agent 用 `workflow_run` 发起，传需求名 `title`、目标与完成标准 `goal`，以及建议的做法 `way`（`simple` 或 `develop`，默认 `develop`）；也可以带 `devices`、`device`、`hold`、`reviewer`、`reviewer2`、`branch`、`base`，默认值与对应的开发流程相同。

| 输入 | 用途 |
| --- | --- |
| `title` | 需求名，必填，也是 PR 标题 |
| `goal` | 目标与完成标准，必填，写成可以照着做的完整描述；监督开发时可以写大致分哪几块、碰不碰后端 |
| `way` | Agent 建议的做法：`simple`（简易开发）或 `develop`（监督开发），默认 `develop` |
| `devices` | 「设备验收」，默认关；卡上两个开工选项的勾选默认取它 |
| `device` | 「验收设备」，如 `duo-testbed`，默认空；验收期间独占它 |
| `hold` | 「验收时占用」，监督开发的安装与设备验收期间另外占着的组，默认空；见「监督开发」的「设备占用」 |
| `reviewer`、`reviewer2` | 监督开发的「整体评审者」「第二整体评审者」，各是一组 Agent 选择，没有默认值，不填就不评（见「监督开发」的「整体评审」） |
| `branch` | 简易开发提交改动的「分支」，默认是会话所在的分支（`defaultFrom="session.branch"`）；开在别的目录时会话没有分支，简易开发从目标分支替主 Agent 开一条 |
| `base` | 「目标分支」，留空用仓库默认分支 |

「开工」卡批的是需求：写需求名、目标与完成标准、Agent 建议的做法、设备验收的建议（填了 `hold` 时连同验收期间占用的组），以及两个整体评审者位置各是谁（Agent · 模型 · 强度，没填写「未指定」）。
评审者这两行只读，要换人选「先别」并在附言里说明。卡上不列执行者：监督开发里每个泳道 PR 的执行者、备用执行者和评审者由主 Agent 发起泳道 PR 时自己定。
选项是「开工：简易开发」「开工：监督开发」和「先别」。两个开工选项各带勾选项「设备验收」，默认取 `devices`；卡上的附言可选。

- 选简易开发：调用 `simple`，传 `branch`、按勾选得到的 `devices`、`device`、`base`。泳道由发起的 Agent 负责：开在别的目录、或要指定分支时，发起时就传 `branch`（分支可以之后再开，开始时只核对名字）；没传时 `simple` 从目标分支开 `agent/simple-<运行 ID>` 并告诉它。
- 选监督开发：调用 `develop`，传 `title`、`goal`（你在卡上写了附言时，在 `goal` 后另起一行「用户开工时补充：」接上附言）、按勾选得到的 `devices`、`device`、`hold`、`reviewer`、`reviewer2`、`base`。
- 选「先别」：不调用任何流程，直接结束，结束输出说明用户没有开工；有附言就一并带上。

被调用流程正常结束时的 `pr`、`commit` 原样成为「开工」的输出，`notify` 用来决定是否叫醒发起会话：结束时是否叫醒跟随被调用流程批准卡上「全部完成后通知 Agent」的勾选；监督开发被放弃和「先别」都会叫醒。

## 监督开发

一个需求开一次「监督开发」（`develop`），对应一条泳道 `lane/<运行 ID>`。和主 Agent 把需求聊清楚后，在会话的流程里开启它，或让 Agent 发起「开工」并在开工卡上选「开工：监督开发」。
中间的事都由主 Agent 负责：它用「泳道 PR」（`lane-pr`，见下一节）把需求一块块交给执行者，每个泳道 PR 经项目检查、评审和它的审查后合进泳道，这期间不找你；
它判断需求做完后「提交验收」，泳道才开 PR 进目标分支，经检查、整体评审和设备验收后，由你批准一次，用合并提交合并，再按勾选部署、发布。
它是手动流程，不订阅 PR 事件，也不依赖 review 插件（评审按名字调用能力 `review-commit`）；它开的 PR 不会启动 PR 生命流程（见下文「不触发 PR 生命流程」）。

| 输入 | 用途 |
| --- | --- |
| `title`、`goal` | 需求名（也是 PR 标题）和目标与完成标准，默认空。你开启时留空，由主 Agent 写；「开工」和需求交付发起时传这两项 |
| `devices` | 布尔值「设备验收」，默认关；改了客户端、要在 Mac 或 iPhone 上验收时打开 |
| `device` | 可选文本「验收设备」，如 `duo-testbed`，默认空；开启设备验收且非空时，从安装前到验收结束独占这台设备；留空不占设备 |
| `hold` | 可选文本「验收时占用」，一个组名，默认空；开启设备验收且非空时，安装与验收期间另外占着这个组（容量 1），如项目的泳道专用后端；留空不占 |
| `delivery` | 字符串「所属需求交付」，填需求交付（`deliver`）运行的 ID；默认空，为独立交付 |
| `reviewer`、`reviewer2` | 「整体评审者」「第二整体评审者」，各是一组 Agent 选择（流程参数的 `agent` 类型），没有默认值，不填就是空（`null`）、不评；见下文「整体评审」 |
| `base` | 「目标分支」，留空从 GitHub 读取仓库默认分支 |

0. 没有目标时（你直接在会话里开启的），先交主 Agent「写需求」：这张任务不叫醒它（`coda:wake="false"`），随你在会话里的下一条消息告诉它，说明你开启了监督开发、它要做什么。经「开工」发起时 `title` 和 `goal` 已由开工卡交过来，不经过这张任务。主 Agent 答复时备注必填：第一行是需求名，空一行后是目标与完成标准；缺一样回到这张任务。
1. **建泳道**：从远端目标分支的最新提交建 `lane/<运行 ID>` 并推送，分支名只用 ASCII。远端已有同名泳道时沿用它，不重建：运行从头重跑时不会因为分支已存在而失败，也不会丢掉已合进泳道的改动。
2. **需求进行中**：交主 Agent 一张「需求进行中」任务，可以挂好几天。任务里写着需求、目标、泳道，以及怎么推进：
   - 每一块用 `workflow_run` 发起一个泳道 PR：传 `lane`（本运行的 ID）、`title`、`task`，以及这一块的 `executor`、`executor2`、`reviewer`、`reviewer2`、`reviewerOnce`（主 Agent 按这一块的性质逐个定）；
   - 互不依赖的块可以同时发起，有依赖的等前一个合进泳道再发起；
   - 跟上目标分支用 `sync=true` 的泳道 PR；
   - 中途想先看效果，可以用泳道的提交发起 `mac-preview-install`、`ios-preview-install`，或对泳道 head 跑一次合并前检查（`kind=premerge`）。

   答复有三种：
   - 「提交验收」：备注必填，是写给你的改动汇报（做了什么、需要你知道的风险或没做的），放在批准卡和 PR 描述最上面，每次提交以最新一份为准；进入收尾。
   - 「暂停」：备注必填，写为什么停、等什么。转成你手上的「需求已暂停」卡，卡上是这段备注；你选「继续」回到「需求进行中」（附言随原因交给主 Agent），选「放弃」结束。这样主 Agent 不会每次空下来又被叫醒。
   - 「放弃」：结束这次运行，泳道保留。

   必填备注没写（含只写空白）时回到同一张任务说明缺什么。每次回到「需求进行中」，任务里都写着回来的原因：检查失败的运行与步骤、设备验收的意见与截图路径、你暂不合并的原因、整体评审后主 Agent 的说明等；主 Agent 提修复用的泳道 PR，再重新「提交验收」。
3. **开 PR**：开或更新泳道进目标分支的 PR，标题是需求名。正文依次是主 Agent 最近一次「提交验收」的汇报、合进泳道的泳道 PR 列表（标题与链接，按编号先后）、改动区域统计（下文「改动区域」），三者合称汇总，批准卡和待交付卡贴的就是它。
   泳道 PR 列表用 `gh pr list --base lane/<运行 ID> --state merged` 从 GitHub 读；已开着的 PR 也用 `gh pr list --head lane/<运行 ID> --state open` 从 GitHub 找。需求跨好几天，从头重跑时只重建收尾，不靠运行暂存。
4. **检查**：独立交付开了设备验收（`devices=true`、`delivery` 留空）时，开 PR 后与检查并行调用项目的 `coda:kind="prebuild"`（预编）流程，传泳道 head，填了 `device` 时另传 `device`；它为随后验收要装的客户端先编好，检查不等它，它失败只留在调用记录里，安装流程到时照常自己构建，项目没有这类流程时立即结束。项目检查已在各泳道 PR 上跑过；泳道 head 是本运行已通过检查的同一提交时复用，否则在它上面跑一次 `kind=check`。随后在泳道 head 上跑一次 `kind=premerge`（合并前检查，放每个版本都跑嫌贵的验证），再等 GitHub 检查：核对 PR 的 `headRefOid` 与泳道 head 一致，每 10 秒查询一次检查，最多等 120 秒登记；出现检查后用 `gh pr checks <PR> --watch` 等全部结束，并再次核对 head。连续 120 秒为空才按无 CI 通过，日志明确记录这一判断（有界等待是为了兼容 GitHub Actions 和外部 CI，不猜测 workflow 的事件、路径或分支过滤；超过窗口才登记的 CI 不在保证范围内）。任何一项失败都带着运行链接回到「需求进行中」，主 Agent 用 `workflow_status` 读失败的流程、步骤和日志。
5. **整体评审**：填了整体评审者时，对整条泳道评一次（下文「整体评审」），发现交主 Agent 选「继续验收」或「回到进行中」。都不填就跳过。
6. **设备验收**：`devices=true` 且 `delivery` 留空时进入「安装与设备验收」段。主 Agent 用 `workflow_run` 带泳道 head 的精确 `commit` 只安装改到的那一端（`mac-preview-install`、`ios-preview-install`），发起的安装都成功后答复「已装好」；要先修改时选「回到进行中」，备注必填，缺少时返回安装卡。随后你答复「设备验收」，「不行」必须附言（写意见或附截图，`note="required"`），意见与截图路径带回「需求进行中」。改了后端、项目允许从泳道部署后端时，主 Agent 按项目的说明同样带泳道 head 发起后端部署；填了 `hold` 时本段占着那个组（下文「设备占用」）。验收通过后流程用 `tell-session` 告诉主 Agent，接下来等你批准。
7. **批准**：`delivery` 非空时进入给主 Agent 的「待交付」（见下文），不出你的批准卡。否则你在「批准合并」卡上决定：卡上是汇总和已通过的检查；「部署」「发布预览版」「发布正式版」各自仅在项目有 `kind=deploy`、`kind=preview`、`kind=release` 的流程时显示，默认都不勾；「合并」另有「全部完成后通知 Agent」，默认勾选。「暂不合并」必须附言，原因带回「需求进行中」交给主 Agent 跟进。批准后直接合并，不再跑检查。
8. **合并**：用合并提交合并：`gh pr merge --repo <host/owner/repo> --merge --match-head-commit <泳道 head> --delete-branch`。目标分支的 first-parent 历史里每个需求一个提交（按 first-parent 计数的构建号照常算），泳道里每个泳道 PR 一个提交，可以二分、可以单独回退。
   合并前查询 PR 状态：已合并且 head 与本次记录一致时直接输出原合并提交；已合并但 head 不一致或已关闭未合并时明确报错。合并命令失败后查询一次 PR，仅在仍 OPEN 且 `mergeable=CONFLICTING` 时带着原因回到「需求进行中」：主 Agent 发起 `sync=true` 的泳道 PR 把最新目标分支合进来、解冲突、顺延撞号的迁移版本，再提交验收；之后重新跑检查、出新的批准卡，部署、发布选项以新卡为准。其余合并失败保留原退出码，不依赖错误文案判断冲突。仓库从 PR URL 取得，gh 只删除远端泳道、不操作本地分支，支持分离 HEAD 检出，也兼容 GitHub 合并后自动删除分支。
   成功后在合并提交上按勾选依次运行 deploy、preview、release，每类一次；预览和正式发布均传所选发布说明 `notes`，正式发布另传 `publish: "true"`。勾选发布但备注为空时，先交主 Agent「写发布说明」：列出所选类别，由它按上次公开版本以来合并的改动写面向用户的说明，备注必填，空白时返回同一任务；你自己填了备注就直接用。审查意见不作为发布说明。

「全部完成后通知 Agent」控制最外层结束事件的 `coda:notify`：取消勾选后，合并及所选部署、发布全部成功时不叫醒发起会话，只在下一轮顺带告知结果；失败仍叫醒。依赖 Coda #2107 的结束通知支持。

`delivery` 非空时（成员需求运行，由需求交付发起），检查和整体评审之后进入给主 Agent 的「待交付」，跳过安装和设备验收，不受 `devices` 影响。任务列出所属需求交付、PR、head、泳道和汇总：

- 「退回修改」备注必填，缺少则返回待交付；意见带回「需求进行中」，提泳道 PR 修好后重新提交验收、跑检查，再回到待交付。
- 「放行合并」由主 Agent 按需求交付运行的顺序选择，随后以合并提交合并（合并前检查已在待交付前跑过）；合并成功输出合并提交并结束，仍通知发起会话，不部署。

运行之间只通过主 Agent 答复各自的人工任务协调，不直接发消息，也不依赖跨仓库原生子运行。反馈与汇报暂存于 `$CODA_ARTIFACTS/develop.json`；长期结果在泳道、泳道 PR 与进目标分支的 PR 里。

### 整体评审

填了 `reviewer` 或 `reviewer2` 时，GitHub 检查通过后进入子流程「整体评审」（`coda:optional`，只在走进去时出现在卡片上）：两个位置各一份、同时进行，没填的直接结束、记为跳过；
填了的用 `callActivity calledElement="review-commit"` 按名字调用评审能力，`base` 是目标分支的最新提交、`head` 是泳道 head（评的是两者的三点 diff，即整条泳道）、`task` 是需求名、目标与完成标准和主 Agent 的汇报、`evidence` 是项目检查结果并注明合并前检查与 GitHub 检查已通过。
评审没完成时 `review-commit` 照常结束（`decision` 为 `INCOMPLETE`），调用本身没成时出错边界接住，都照常结束、不重试。

随后主 Agent 收到「整体评审结论」，列出每位的结论与发现（写法与泳道 PR 审查卡上的「评审者的发现」相同，原文在 `$CODA_ARTIFACTS/reviews.md`，卡上给出路径）。发现成不成立由它判断：选「继续验收」往下走；选「回到进行中」时备注可选，连同评审原文的路径带回「需求进行中」，主 Agent 提泳道 PR 修好后再提交验收。

### 改动区域

PR 汇总的改动块统计目标分支最新提交与泳道 head 的三点 diff（与 GitHub PR 的 Files changed 一致），按区域列出文件数和增删行数，区域按增删总行数从多到少排。改名按新路径归类，二进制文件计入文件数、行数记 0。

区域由泳道 head 上的 `.coda/areas.json` 声明，格式为 `{ "区域名": ["路径前缀", ...] }`，前缀是普通字符串前缀，如 `iOS/`、`Sources/CodaCore/`、`AGENTS.md`。一个文件归入最长匹配前缀所在的区域；都不匹配时归到它的顶层目录名，根目录下的文件归「根目录」。没有这个文件时全部按顶层目录归类；文件存在但 JSON 写坏时开 PR 步骤直接失败。

### 设备占用

填写 `device` 且开启设备验收时，安装前先调用 testbed 的 `resolve-testbed` 按设备名解析，再用 `hold-group` 占用返回的组（容量 1），状态显示「等验收设备 <设备名>」。引擎按组归属在整个空间排队；composer 不新增 testbed 硬依赖；填写设备名使用验收时须安装 testbed。安装与验收共用这一段占用，发起 `ios-preview-install` 时除精确 `commit` 外还传同一个 `device`，安装运行借用本段设备，不另排队。通过、回到进行中或取消并收尾后释放；再次进入重新排队。缺少必填意见时仍留在本段补填。未填设备名时不传设备参数、不占设备。

填写 `hold` 时，占完验收设备之后再用 `hold-group` 占着这个组（容量 1），状态显示「等 <组名>」；先设备、后这个组，顺序固定，两条运行不会互相等住。它给项目里同一时间只能给一个需求用的东西，如只有一台的泳道专用后端：项目的部署流程整条运行占着同一个组，主 Agent 在安装卡上发起的部署借用本段的组直接进，别的运行（如别的需求合并后的部署）排在本段之后。组名和要发起哪个流程由项目自己说明，composer 只照传的组名占。和设备一样，离开本段就放开，再次进入重新排队；留空不占。

### 不触发 PR 生命流程

流程步骤替运行所属的会话说话（`CODA_THREAD_ID`），GitHub 插件的 `gh` 会把它 `gh pr create` 开的 PR 报给「PR 观察」，PR 观察再发布 `pull_request.opened` 等事件，review 插件的 PR 生命流程（`pull-request`）就会自动跟上同一个 PR：
它会再跑一遍检查、评审，进目标分支的 PR 还会再出一张批准卡。所以监督开发和泳道 PR 开 PR 时去掉 `CODA_THREAD_ID`（`scripts/shared.mjs` 的 `openPr`），这个 PR 不上报，PR 观察和 PR 生命流程都不会因它启动；检查、评审、合并都由开它的流程自己做。
代价是这个 PR 不在会话的「报过的 PR」里（GitHub 插件的 `github-reported-pr` 找不到它），要手动评审时直接传 PR 地址。

## 泳道 PR

「泳道 PR」（`lane-pr`）是需求运行里的一块改动：主 Agent 在「需求进行中」用 `workflow_run` 发起，执行者写代码，经项目检查、评审和主 Agent 的审查后合进泳道，结果交回发起的会话。
它不出你的卡片、不装机、不部署、不跑合并前检查（这些只在泳道进目标分支时做一次）。一项就是一个泳道 PR，下一项另开一个；互不依赖的可以同时跑。

| 输入 | 用途 |
| --- | --- |
| `lane` | 必填，需求运行的 ID，泳道是 `lane/<它>` |
| `title` | 必填，泳道 PR 的标题 |
| `task` | 必填，自足的任务书：背景、范围与验收要求 |
| `sync` | 布尔值「跟上目标分支」，默认关；见下文「跟上目标分支」 |
| `executor` | 「执行者」，一组 Agent 选择（Agent、模型、强度、模式与其他选项，流程参数的 `agent` 类型）；默认取发起会话的，跨目录发起取不到时也用发起会话的。没选的模型、强度、模式用执行者的默认值，其他选项逐个传给 `coda-agent --option` |
| `executor2` | 「备用执行者」，没有默认值，不填就是空（`null`）；见下文「备用执行者与退回次数」 |
| `reviewer`、`reviewer2`、`reviewerOnce` | 「评审者」「第二评审者」「首次评审者」，没有默认值，不填就不评。前两位评每一次交付，首次评审者只评每个执行会话第一次通过项目检查的那次交付；见下文「评审」 |

1. **执行**：用 `coda-agent --commit <泳道当前 head> --json` 开执行会话。固定说明要求遵守 AGENTS.md，只做本项、在当前分支提交、不推送、不写防御性或冗余代码、不顺手重构；只跑与改动直接相关的快检查，流程会在审查前自己跑项目检查，构建、全套和界面检查不重复跑，不必再用 run-held 跑整套编译；并报告实际验证。
   执行者的分支/head 必须在本机仓库可读；`coda-agent --json` 标准输出是一行 `{session, branch, head, answer}`，`--continue` 保留同一会话并遵守首次的退出码约定。
2. **推送并开 PR**：把执行者的 head 强推到本运行的分支 `lane-pr/<运行 ID>`；第一次交付时开 PR，base 是泳道、标题是 `title`、正文写明它由 `lane-pr` 开、合进哪条泳道、运行链接和任务原文；之后的交付推同一个分支，就是更新同一个 PR。开 PR 时不带会话，不触发 PR 生命流程（见「监督开发」的「不触发 PR 生命流程」）。推送失败停在这一步，日志保留 Git 的具体原因。
3. **项目检查**：在这个 head 上跑项目的 `coda:kind="check"`。失败时前两次自动交回同一执行会话，写明提交和本运行链接，由执行者用 `workflow_status` 读失败流程、步骤和日志；第三次连同三次记录交给主 Agent 审查，不评审。通过会清零连续失败次数。
4. **评审**：见下文「评审」。
5. **主 Agent 审查**：列出泳道 PR、执行会话、分支、head、泳道、看改动的命令（`git fetch origin <泳道>` 后 `git diff FETCH_HEAD...<head>`）、退回次数、备用执行者、项目检查结果、执行者回答、评审者的发现和待处理反馈。答复有五种：
   - 「退回修改」：备注必填，同一个执行会话（`--continue`）继续修改。
   - 「让执行者合并泳道」：备注可选；同一个执行会话把泳道当前 head 合进来（见下文「合并泳道」），不算退回。
   - 「换备用执行者重做」：备注必填；见下文「备用执行者与退回次数」。
   - 「合进泳道」：见下文「合进泳道」。
   - 「放弃」：`gh pr close --delete-branch` 关闭这个 PR、删除分支，泳道不动，运行结束。

   必填备注没写时回到审查卡，「待处理反馈」里写明缺什么。审查要点、评审发现由主 Agent 判断成不成立，修改都交给执行者，主 Agent 不自己改代码。

运行结束（合进泳道或放弃）时叫醒发起的会话（`coda:notify="true"`），输出 `pr`，合进泳道时另有 `commit`（squash 得到的提交；跟上目标分支的是泳道快进到的 head）。执行会话、PR 与反馈暂存于 `$CODA_ARTIFACTS/lane-pr.json`。

### 合进泳道

主 Agent 选「合进泳道」后，流程先 fetch 泳道当前 head，因为并行的泳道 PR 可能刚合进去：

- 普通泳道 PR 用 `git merge-tree --write-tree` 试合并泳道 head 与这次交付。只是试：不产生提交，不动任何引用、索引和工作区（只会在对象库里留下几个可回收的临时对象）；冲突时能按文件名列出。
  有冲突就不动泳道，把下文的固定说明连同冲突的文件交给同一个执行会话继续，之后照常推送、检查、评审，再回到审查卡，不算退回。
  干净时用 `gh pr merge --repo <host/owner/repo> --squash --match-head-commit <head> --delete-branch` 合进泳道。已合并且 head 一致（重跑这一步）时直接给原合并提交；合并失败且 GitHub 说与泳道冲突时同样交回执行者合并泳道；其余失败保留原退出码。
- 跟上目标分支的泳道 PR（`sync=true`）只能快进：泳道 head 是这次交付的祖先时，把泳道推到这次交付的 head（不强推），GitHub 会把这个 PR 标为已合并；不是祖先时同样交回执行者先合并泳道（能干净合并时不列冲突文件）。不 squash，也不删除分支。

### 合并泳道

「让执行者合并泳道」和试合并发现冲突给执行者的是同一段固定说明：泳道是哪一条、别的泳道 PR 可能已经合进去了，试合并时列出冲突的文件；要求先 `git fetch origin <泳道>`，把它合并（不是变基）进当前分支——变基会改写已经审查过的提交；解决冲突，数据库迁移等版本号和泳道撞号时顺延自己这边的；跑和冲突相关的测试后提交，只做这件事，回报冲突了哪些文件、各自怎么解决的、跑了什么；泳道没有新提交时直接回报不需要合并。主 Agent 写了备注就附在后面。两种都不加退回次数；因为是同一个会话继续，之后的交付不算第一次交付，首次评审者不再评。

### 跟上目标分支

泳道活得久，目标分支动得快。主 Agent 专门发起一个 `sync=true` 的泳道 PR，任务写把目标分支合进来、解冲突、顺延撞号的迁移版本。流程在任务书后附上固定说明：把目标分支合并（merge）进当前分支，不要变基、不要压成一个提交；它会快进进泳道，保住泳道与目标分支的祖先关系；迁移版本号撞号时顺延泳道这边的。
合进泳道时用快进而不是 squash：squash 会丢掉与目标分支的祖先关系，之后泳道进目标分支时同样的冲突会再来一遍。

### 评审

评审在项目检查通过（「记录通过的检查」）之后、「整理审查材料」之前；检查没过不评，连续三次检查失败直接交主 Agent 审查的那条路也不经过它。
三个位置都没填（或只填了首次评审者、这次不是第一次交付）时不进入评审。否则进入子流程「评审」（`coda:optional`）：三个位置各一份、同时进行（多实例），每份都走到自己的结束事件，三份都结束才往下走：

- 这一位没填（首次评审者在同一执行会话的后续交付上算没填）：直接结束，记为跳过；
- 填了：`callActivity calledElement="review-commit"` 按名字调用评审能力，`base` 是泳道当前 head（评的是三点 diff，别的泳道 PR 合进泳道、或执行者合并了泳道都不混进来）、`head` 是这次推送的提交、`task` 是任务书、`reviewer` 是这个位置、`evidence`（已有验证）是这次交付的项目检查结果；
  它和审查卡上「项目检查结果」是同一段文字（每个检查一行：流程名、结果、运行链接；项目没有声明检查流程时就是那一句说明），评审者不必再去 GitHub 找检查记录；传 `evidence` 需要 review 插件 2.17.0 及以上；
- 评审没完成（评审方会话重试后仍失败，或回复末尾没有合格的结论）：`review-commit` 照常结束，`decision` 为 `INCOMPLETE`，`line` 写明原因；不算这一步失败，免得几位同时评不成让运行「叫不动」；
- 调用本身没成（没有插件提供 `review-commit`、参数不合法；评审步骤到了 120 分钟时限也落在这里）：挂在调用上的出错边界接住，记为「没评成」，照常结束。两种都不重试、不换人。

「第一次交付」从开新执行会话（「执行这一项」或「换备用执行者重做」）算起，是这个会话第一次通过项目检查的那次；同一会话「退回修改」、合并泳道后的再次交付不算。

「整理审查材料」只取评的是这次交付（执行者当前 head）的结果，审查卡在执行者回答之后多一段「评审者的发现」：每位一小节，写明是哪个位置、它的 Agent · 模型 · 强度、一句话结论，再列每条发现的严重程度、标题、位置和说明（标题、位置里的换行压成空格）；
评审没完成的写「没评成：」加原因，调用本身没成的写「没评成」并指向本运行里那一步（流程读不到被调用运行的失败原因，主 Agent 用 `workflow_status` 看）。没有评审时这一段不出现。
全部发现的说明与每位评审者的原文写在 `$CODA_ARTIFACTS/reviews.md`，卡上给出路径。卡片正文的 4000 字上限是协议对 BPMN 里 `documentation` 字面的检查，展开 `{{…}}` 后的文字不受它限制；这一段仍按 4000 字收着：放不下时卡上每条只留严重程度、标题和位置，说明在上面的文件里。

需要 0.3.32 及以上的 Coda（Coda #2435）：没填的评审者、备用执行者是空的 Agent 参数，按名字调用时要算作没传，旧版会让这次调用失败。

### 备用执行者与退回次数

- 「换备用执行者重做」的备注写为什么换、接手的人要注意什么。流程用 `executor2` 从泳道当前 head 新开一个执行会话，重做同一项：上一位没被接受的提交不带过来；给它的是固定的执行者说明、这一项的任务书原文、这次的备注，再加一句上一位执行者的分支与提交在哪里、可以参考也可以不用。
- 之后照常推送、检查、评审、审查。新会话的第一次交付算第一次（首次评审者要评），连续检查失败的计数也重新开始；再「退回修改」续的是新会话。主 Agent 可以再换一次，同样新开一个备用执行者的会话。换不换只由主 Agent 决定，流程不按退回次数自己换。
- 没填 `executor2` 时不能换。Coda 的流程方言只能按条件隐藏勾选项（`coda:option` 的 `coda:shown`），不能隐藏答复本身，所以这个答复总在卡上：卡上写着「备用执行者：未指定，不能换人」；选了就回到审查卡，「待处理反馈」里写明没有填备用执行者，运行不失败。

审查卡写「这一项已退回 N 次」，0 次也写。只有主 Agent 选「退回修改」（备注写了）才加一；项目检查失败的自动续作、换备用执行者、合并泳道（两种都是）、备注没写回到卡上都不算；同一项换人不归零。

## 需求交付流程

一个需求跨几个仓库、要一起验收、一起批准时才用它；单仓库的需求直接用监督开发。在**交付并部署这个需求的项目**的会话里开启「需求交付」（`deliver`）：`title`（需求名）、`goal`（目标与完成标准）默认空，`devices`（是否设备验收）默认关，可选 `device`（验收设备名，如 `duo-testbed`，默认空），与监督开发的设备占用规则相同。

0. 没有目标时（你开启的），先交主 Agent「写需求」，同样不叫醒它、随下一条消息告诉它。主 Agent 答复时备注必填：第一行需求名，空一行后是目标与完成标准。任务里写明之后怎么做：为每个要改的仓库在那里用 `workflow_run` 发起 `develop`（成员需求运行），传 `title`、`goal`（这个仓库要做的部分与完成标准）、`delivery=<本运行 ID>`、`devices=false`，跨仓库用 `project`；主 Agent 在各成员的「需求进行中」用泳道 PR 把改动合进它的泳道，做完提交验收，检查通过后停在「待交付」。

1. 主 Agent 在「确认达标」选择「开始交付」，备注每行一个成员 PR URL（各泳道进目标分支的 PR），按合并顺序排列，被依赖的仓库在前。流程记录各 PR 的 URL、head、分支及 base；选择「放弃」结束。
2. 开启设备验收时，以最新 `origin/<base>` 创建 `delivery/<运行 ID>`（分支名只用 ASCII），按顺序 `git merge --no-ff` 仅合入本仓库成员的已记录 head 并推送。集成失败经错误边界回到确认，合并冲突的具体 Git 输出作为反馈。新一轮从最新 base 重新集成并替换本运行的预览分支。
3. 主 Agent 用集成提交只安装改到的那一端（`mac-preview-install`、`ios-preview-install`），发起的安装都成功后答「已装好」；「回到确认」须附原因。用户统一设备验收一次，「不行」须附意见并回到确认。主 Agent 在相关成员的「待交付」选「退回修改」，它回到「需求进行中」，提泳道 PR 修好、重新提交验收并检查通过后再集成、安装、验收。`devices=false` 跳过集成、安装及设备验收。
4. 主 Agent 写约 15 行以内的交付汇报，备注作为批准卡正文：交付名、用户能感知的 3～5 条变化、结构变化（无则写「无」）、设备与检查结论、部署后真实环境验证计划、风险与未做事项（没有可省略）、PR 链接。不放执行者原文、测试数量、文件清单或代码。
5. 用户「批准交付」卡显示汇报和全部成员 PR；「批准合并」提供「部署」「发布预览版」「发布正式版」，各自仅在项目有 `kind=deploy`、`kind=preview`、`kind=release` 的流程时显示，默认都不勾。「暂不合并」必须附言（原因）并返回确认；设备验收的「不行」同样必须附言，可以只附截图，路径随反馈交回主 Agent。批准后，若勾选发布但备注为空，先交主 Agent「写发布说明」，再进入「放行合并」；否则直接进入「放行合并」。由任务叫醒发起会话，不再单独通知选择。
6. 主 Agent 按顺序放行成员，被依赖的仓库在前：先放行提供被钉版本的包的成员的「待交付」，等合并并发布新版本；再退回钉这些包的仓库成员，回到它的「需求进行中」提泳道 PR 更新钉定的包版本，重新提交验收、检查通过后回到待交付；最后放行依赖方成员。成员都以合并提交合并。全部合并后备注写本项目最后一个合并提交，没有本仓库成员时写本项目当前目标分支提交。
7. 在该合并提交上按勾选依次调用 `run-workflows` 的 deploy、preview、release 三类，每类一次；每类调用项目的全部对应流程，预览和正式发布均传所选发布说明 `notes`；正式发布另传 `publish: "true"`。随后主 Agent 按 `goal` 走真实环境验证，选「通过」或附具体意见选「有问题」，用 `tell-session` 告知发起会话后结束。未勾部署时仍验证当前真实环境，备注说明未部署造成的未验证部分。

必填备注缺少时回原任务补填。成员快照、轮次和反馈保存在 `$CODA_ARTIFACTS/deliver.json`；运行之间只通过主 Agent 答复各自人工任务协调，不直接发消息。此流程不改变成员需求运行的检查与合并路径。

测试在 `test/plugins/composer/`，用临时 Git 仓库及假的 coda-agent、gh 验证，不发真实 PR 或部署。网关条件用同版本 FEEL 求值真实 BPMN（脚本输出先照引擎把 `"true"` / `"false"` 转为布尔值），覆盖泳道 PR 的开 PR、更新、squash 与快进合进泳道、试合并冲突，需求运行的建泳道与沿用、进行中的三种答复、PR 正文、检查复用、各处失败回到进行中与合并方式；check 包仅校验流程方言，这些测试不运行完整 BPMN 引擎。设备验收段测试覆盖有无设备时的分流、占用范围、退出和重入路径。
