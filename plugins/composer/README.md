# 输入框模式

`@coda-console/composer` 把输入框的五种模式放在同一个插件里，插件 ID 为 `composer`；Ultra 让主 Agent 把代码修改交给开发流程、亲自审查，多个功能一起交付时再按需求统一验收。

| 模式 | 入口 | 用途 |
| --- | --- | --- |
| 交接到新会话 | `/handoff` | 新会话承接当前上下文，共享工作目录；原会话保留，可继续使用。 |
| 子会话 | `/subagent` | 从任意会话启动子会话，承接近期上下文并沿用工作目录；可选完成后回报父会话或你。 |
| 执行命令 | `!` | 在会话工作目录执行命令，命令与结果作为消息发给 Agent；也可在新任务输入框使用。 |
| Ultra | `/ultra` | 一个需求默认一个开发流程直接到合并；多个功能一起交付时再建需求流程统一验收。主 Agent 亲自审查、判断达标；也可在新任务输入框使用。 |
| 循环 | `/loop` | 按周期把同一句话再发给 Agent，每轮做完才开始计时，7 天后自动结束；仅用于已有会话。 |

五个模式可同时开启，模式 ID 不变。Ultra 开启时，从这个输入框创建的新会话（包括子会话、交接和新任务）继承 Ultra 及当前子 Agent 名单，各自独立保留模式；关闭来源的 Ultra 不会关闭已创建会话的 Ultra。工具栏始终选择输入框自己的执行者；交接与子会话的参数另有可选 Agent，留空沿用输入框执行者。子会话也能创建自己的子会话。

3.0.0 按 [Coda #2063 的接口约定](https://github.com/coda-console/coda/issues/2063) 改为 `submissions` 协议参与者，依赖该 issue 第 2 步的后端支持，以及 [Coda #2085](https://github.com/coda-console/coda/pull/2085) 的新会话模式继承与实际投递计数，不能用于旧版回调宿主。交接、子会话和循环声明 `once: true`，发出的一条被收下后退出该模式；Ultra 保持开启，执行命令的触发词仍是 `!`。

插件只返回补充，不改正文、附件、引用或输入框的执行者。多个模式的补充由 Coda 合并，`tell` 是字符串数组，按列表追加后随这条发送到每个收到它的会话；只要有一项 `divert: true` 就不发给默认去向，各模式追加的去向仍分别执行。

| 模式 | 发出的一条的补充 |
| --- | --- |
| 交接 | `divert: true`，追加 `thread` 去向，带 `handoffSource`、可选 `agent`、`open: true` |
| 子会话 | `divert: true`，追加 `thread` 去向，带 `handoffSource`、`parentThreadId`、`replyTo`、可选 `agent`、`open: true` |
| Ultra | 首条、参数变化后的首条，以及创建新会话时返回完整开启说明；此后 `sent > 0 && sent % 10 === 0` 时返回仍在说明，其余返回 `null` |
| 循环 | `divert: true`，追加 `loop` 去向，带 `thread`、`every` |
| `!` | `divert: true`，会话中追加 `message` 去向，带 `thread`、`run: true`；新任务中追加 `thread` 去向，带 `run: true`、`open: true` |

新会话去向明确跳转，客户端按每项 `open` 执行。Coda 将非一次性、非触发式且适用于会话的模式和参数写入新会话输入框；各会话只为自己实际收到的模式消息计数，转发到新会话不增加来源的 `sent`。空 Agent 不写入目标，交由 Coda 沿用 `spec.agent`（包括 settings）。

## 循环用法

在已有会话的输入框里打 `/loop`，填写每轮要做的事，选择周期后点「开始循环」。周期默认 30 分钟，可选 5 分钟、10 分钟、15 分钟、30 分钟、1 小时、2 小时、3 小时、6 小时、12 小时或 1 天。

这条消息就是第 1 轮；Coda 收下后创建循环，输入框随即退出循环模式。每轮做完才开始计算下一个周期，不叠着跑；7 天后自动结束，也可提前停止，归档会话同样结束循环。计时与重发由 Coda 后端负责，会话进程被回收后仍会按时恢复。

循环的计时行为沿用 [Coda #2051](https://github.com/coda-console/coda/pull/2051)，3.0.0 通过上述 `loop` 去向提交。

## Ultra 模板设置改名

Ultra 的模板设置由 `ultra.templates` 改为 **`composer.templates`**，模板的数据结构不变。清单的预设只引用新设置名，由 Coda 按输入框所在目录读取。
旧 Ultra 包暂时保留，旧设置迁移和卸载旧插件由 [Coda issue #2050](https://github.com/coda-console/coda/issues/2050) 的第 4 步处理，本插件不自行迁移。

## Ultra 用法

在会话或新任务输入框打 `/ultra`，点模式条选择执行者名单；点 × 退出。单独开启时消息照常发给当前会话，与其他模式一起开启时按各模式的去向发送。
主 Agent 定义任务、处理困难决策并亲自审查架构和实现方式。所有代码修改通过 `workflow_run` 发起 `develop`，同一运行内按顺序派任务；除非用户另有要求，一次只推进一个需求。
一个需求默认在它改动的仓库发起一个不挂需求的 `develop`（`delivery` 留空），从执行到检查、用户批准与合并在同一个运行里走完；改了客户端、要在 Mac 或 iPhone 上验收时 `devices=true`，否则为 `false`。
一个需求要多个 `develop` 一起验收、一起批准时才用 `deliver`：先在交付并部署它的项目发起，传 `title`、`goal`、`devices` 并记下运行 ID；
每个能独立交付的功能一个 `develop`，传 `delivery=<需求运行 ID>`、`devices=false`，跨仓库用 `project` 指定，可以同时进行。
是否达标由主 Agent 判断，不问用户要不要交付；需求流程达标后在「确认达标」按合并顺序列出成员 PR，被依赖的仓库在前。交付汇报按 deliver 模板写约 15 行，讲交付了什么和结构变化，不放实现细节；在「放行合并」按任务说明顺序操作各 develop 的「待交付」，部署后在真实环境验证。
`spawn` 只用于不改代码的调研、排查和核实，执行者同样从名单选。主 Agent 可以为定任务和审查读代码，不自己实现或替执行者修复。

`composer.templates` 是执行者模板，一行「模板名、Agent、什么时候派给它」。同一模板名的行是一组，进入时填第一组；默认没有模板。
Ultra 参数仍保存为 `subagents`，预设引用 `{ "from": "composer.templates", "by": "template" }`，选择预设只填入名单一次，之后可修改。
develop 和 Coda `spawn` 都按任务从名单选执行者，传 `agent`、`model`、`effort`、`mode`；只有名单为空或没有条目覆盖这项工作时，才用当前会话的 Agent 和模型。
名单中的 `options` 只用于只读 `spawn`，develop v1 不接受它。

`ultra.mjs` 在首条、改参数后的首条、创建新会话时给完整说明，之后每收下 10 条再提醒一次。
主 Agent 每次必须亲自读 diff，检查架构是否得当、改动是否最小、是否有防御性或冗余代码及无关改动；检查通过和执行者汇报不能替代审查。
退回时给具体意见，由同一个执行会话修复；通过后可派下一项，或进入验收。执行者自己完成任务，不继承协调职责、不再转派。
并发已满就等名额；流程或 spawn 不可用就报告阻塞，不改用直接实现或原生子 Agent。用户的明确指令优先。

插件声明 `activationEvents: ["onStartupFinished"]`，重启后通过 `coda.watch('composers', …)` 恢复观察。
Ultra 消失且此前 `sent > 0` 时用 `coda.tell` 告知关闭一次，恢复通常的执行与委派规则；一条都没发过就不说。
名单连同说明超过 Coda 单次告诉 Agent 的 4000 字上限时，缩短名单再发。这些分工是提示词约束，不在运行时禁用工具。

## 开发流程

`workflow_run` 的 `workflow` 传 `develop`。它是手动流程，不订阅 PR 事件，也不依赖 review 插件；使用时停用旧的 PR 生命周期，避免同一个 PR 被两条流程处理。

| 输入 | 用途 |
| --- | --- |
| `title`、`task` | 必填的功能名和第一项自足任务，包含背景、范围与验收要求 |
| `devices` | 必填布尔值「设备验收」，无默认值；改了客户端、要在 Mac 或 iPhone 上验收时传 `true`，否则传 `false` |
| `device` | 可选文本「验收设备」，如 `duo-testbed`，默认空；开启设备验收且非空时，从安装前到验收结束独占这台设备；留空不占设备 |
| `delivery` | 字符串「所属需求」，填需求运行的 ID；默认空，为独立交付 |
| `agent` | 留空使用发起会话的 Agent |
| `model`、`effort`、`mode` | 可选，空值不传给 coda-agent，使用执行者默认值 |
| `base` | 留空从 GitHub 读取仓库默认分支 |

1. 从远端 base 最新提交创建 `lane/<运行 ID>` 并推送，分支名只用 ASCII，不同功能运行各有自己的泳道；PR 标题仍使用功能名。
2. 执行步骤用 `coda-agent --commit <泳道 head> --json` 开执行会话。固定说明要求遵守 AGENTS.md，只做本项、在当前分支提交、不推送、不写防御性或冗余代码、不顺手重构；只跑与改动直接相关的快检查，流程会在审查前自己跑项目检查，构建、全套和界面检查不重复跑，不必再用 run-held 跑整套编译；并报告实际验证。
3. 项目检查通过后，主 Agent 人工任务给出检查运行链接与结果、执行者回答、会话、分支、head 和 `git diff <泳道>...<head>`。退回意见或下一项任务写备注，必填；缺少时返回审查卡。「退回修改」用 `--continue <会话>`；通过后 `git merge --ff-only` 合入泳道并推送，不能快进就失败。「再派一项」从最新泳道提交开新会话。
4. `devices=false` 时，「通过，可以验收」直接进入开 PR 和检查，不产生安装与设备验收任务。`devices=true` 时，主 Agent 用 `workflow_run` 带泳道的精确 `commit` 只安装改到的那一端（`mac-preview-install`、`ios-preview-install`），发起的安装都成功后答复「已装好」；需要先修改（例如合入最新 `origin/<base>`）时选「回到审查」，必须在备注中写具体意见，缺少时返回安装卡。意见作为待处理反馈交回主 Agent，再用「退回修改」继续最近的执行会话。随后用户答复「设备验收」，「不行」须附意见并回主 Agent 审查，修好后重新安装与验收。
5. 设备验收通过或未开启设备验收时，开泳道到 base 的 PR，正文按「第 N 项」汇总各次审查通过的任务：任务原文放在「任务」折叠区，随后列出执行者回答和提交；批准卡片使用同一份正文。项目检查已在审查前对执行者 head 执行；本 develop 记录的通过提交与 PR head 相同时复用，不再调用项目检查。随后核对 PR 的 `headRefOid` 与本轮提交一致，每 10 秒查询一次检查，最多等待 120 秒登记；出现检查后用 `gh pr checks <PR> --watch` 等全部结束，并再次核对 head。连续 120 秒为空才按无 CI 通过，日志明确记录这一判断。选择有界等待是为了兼容 GitHub Actions 和外部 CI，不猜测 workflow 的事件、路径或分支过滤；超过窗口才登记的 CI 不在此判断的保证范围内。审查前项目检查失败时，前两次自动继续同一执行会话，第三次交回主 Agent 并附三次记录；当前内核只能给父运行链接，由执行者用 `workflow_status` 读取失败流程、步骤和日志。GitHub 检查失败仍交回主 Agent。修好后更新同一个 PR 并重跑检查。
6. 用户「批准合并」卡提供「部署」「发布预览版」「发布正式版」，各自仅在项目有 `kind=deploy`、`kind=preview`、`kind=release` 的流程时显示，默认都不勾；选中后运行对应类别的全部流程。「合并」另有「全部完成后通知 Agent」，默认勾选。批准后在同一 head 跑 `kind=premerge`，失败同样回审查，修好后重新检查与批准。
7. 合并前查询 PR 状态：已合并且 head 与本次运行记录一致时，直接输出原合并提交；已合并但 head 不一致或已关闭未合并时明确报错。未合并时用 `gh pr merge --repo <host/owner/repo> --squash --match-head-commit <head> --delete-branch` 合并；仓库从 PR URL 取得，gh 只删除远端泳道分支、不操作本地分支，支持分离 HEAD 检出，也兼容 GitHub 合并后自动删除分支。成功后读取合并提交，再在合并提交上按勾选依次运行 deploy、preview、release，每类一次；预览和正式发布均传所选发布说明 `notes`；正式发布另传 `publish: "true"`。

以上安装、验收和批准路径适用于 `delivery` 留空的独立交付。`delivery` 非空时，「通过，可以验收」直接开或更新 PR，跳过安装和设备验收，不受 `devices` 影响。项目检查及 GitHub 检查通过后，进入给主 Agent 的「待交付」任务，不出用户批准卡。任务列出所属需求、PR、head、泳道和各次审查通过的汇总：

- 「退回修改」备注必填，缺少则返回待交付；意见作为待处理反馈交回主 Agent 审查，再退给最近的执行会话。修好后经审查、更新同一 PR、重跑检查，再回到待交付。
- 「放行合并」由主 Agent 按需求运行的顺序选择，执行现有合并前检查和 squash 合并；检查失败回审查，合并成功输出合并提交并结束，仍通知发起会话，不部署。

所属需求通过主 Agent 在各运行的人工任务里协调，不直接向其他运行发消息，也不依赖跨仓库原生子运行。

独立交付的用户设备验收通过后，流程用 `tell-session` 告诉发起运行的会话功能名，以及接下来开 PR、跑检查；验收不通过的备注已随审查任务交回，不重复通知。用户答复批准卡后直接继续流程，不再单独通知选择。3.6.0 起，独立交付的「全部完成后通知 Agent」控制最外层结束事件的 `coda:notify`：取消勾选后，合并及所选部署、发布全部成功时不叫醒发起会话，只在下一轮顺带告知结果；失败仍叫醒。「暂不合并」仍按原规则叫醒，交由主 Agent 跟进。依赖 Coda #2107 的结束通知支持。

每步独立工作区，进度与已通过的改动暂存于 `$CODA_ARTIFACTS/develop.json`；长期结果在泳道提交与 PR 中。执行者的分支/head 必须在本机仓库可读；`coda-agent --json` 标准输出是一行 `{session, branch, head, answer}`，`--continue` 保留同一会话并遵守首次的退出码约定。需要支持这两个接口的 Coda 版本。

### 审查前检查与当前内核限制

执行者交回后，gate 先把 head 推送到本次运行独占的 `composer-check/<运行 ID>` 分支，成功后才输出 head 并调用项目检查；推送失败停在 gate，日志保留 Git 的具体原因。此时 GitHub 已有提交，检查可以写提交状态，PR 复用同一 head 时也能看到这些状态。临时分支每次 gate 更新，不占用只存审查通过提交的泳道；审查通过并推入泳道后立即删除。推送或清理失败留在原步骤，沿用流程原有的恢复行为；取消或放弃运行可能留下检查分支，不另加全局收尾机制。选择每次运行一个分支，是为了隔离并发运行，且不用累计执行者分支。

流程自己用执行者 head 跑 PR 同一组 `coda:kind="check"`，全部成功后才进入正常审查。审查材料列出检查流程、状态和运行链接；没有声明检查时明确显示没有项目检查。执行者只需跑与改动直接相关的快检查，不必再用 run-held 跑整套编译。通过会清零连续失败次数；新任务重新计数。

用户只需在批准卡勾选发布类别。develop 和 deliver 在勾选发布但备注为空时，进入交给主 Agent 的「写发布说明」任务，列出所选类别，由主 Agent 按上次公开版本以来合并的改动写面向用户的说明；备注必填，空白时返回同一 Agent 任务。用户自己填写了备注则直接使用，不再要求主 Agent 编写。说明随 `notes` 传给两类发布流程，审查意见不作为发布说明。

PR 位于同一 develop 运行，按 head 复用已通过的项目检查即可。iOS 编译由项目检查覆盖，composer 不单独构建预览包，安装流程保持原样。

仍缺少的内核能力只有失败详情输出：错误边界后需要可读取的子运行 ID、失败步骤、错误及日志尾，当前失败批次没有这些 outputs。自动续作目前附父运行和提交，要求执行者读取 `workflow_status`，尚不能直接附日志尾。

填写 `device` 且开启设备验收时，安装前用 `hold-group` 占用 `device:<设备名>`（容量 1），状态显示「等验收设备 <设备名>」。引擎按组归属在整个空间排队；composer 不依赖 testbed 插件。安装与验收共用这一段占用，发起 `ios-preview-install` 时除精确 `commit` 外还传同一个 `device`，安装运行借用本段设备，不另排队。通过、退回审查或确认、取消并收尾后释放；再次进入重新排队。缺少必填意见时仍留在本段补填。未填设备名时沿用原安装与验收行为，不传设备参数、不占设备。

## 需求交付流程

一个需求要多个 `develop` 一起验收、一起批准时才用它；只有一个 `develop` 的需求不挂需求，直接走到合并。在**交付并部署这个需求的项目**用 `workflow_run` 发起 `deliver`，必填 `title`（需求名）、`goal`（目标与完成标准）、`devices`（布尔，是否设备验收）。可选 `device`（验收设备名，如 `duo-testbed`，默认空），与 develop 的设备占用规则相同。各功能独立运行 `develop`，`delivery` 填本需求运行 ID，检查通过后停在「待交付」。

1. 主 Agent 在「确认达标」选择「开始交付」，备注每行一个成员 PR URL，按合并顺序排列，被依赖的仓库在前。流程记录各 PR 的 URL、head、分支及 base；选择「放弃」结束。
2. 开启设备验收时，以最新 `origin/<base>` 创建 `delivery/<运行 ID>`（分支名只用 ASCII），按顺序 `git merge --no-ff` 仅合入本仓库成员的已记录 head 并推送。集成失败经错误边界回到确认，合并冲突的具体 Git 输出作为反馈。新一轮从最新 base 重新集成并替换本运行的预览分支。
3. 主 Agent 用集成提交只安装改到的那一端（`mac-preview-install`、`ios-preview-install`），发起的安装都成功后答「已装好」；「回到确认」须附原因。用户统一设备验收一次，「不行」须附意见并回到确认。主 Agent 在相关成员的「待交付」退回修改，改好并重新检查后再集成、安装、验收。`devices=false` 跳过集成、安装及设备验收。
4. 主 Agent 写约 15 行以内的交付汇报，备注作为批准卡正文：交付名、用户能感知的 3～5 条变化、结构变化（无则写「无」）、设备与检查结论、部署后真实环境验证计划、风险与未做事项（没有可省略）、PR 链接。不放执行者原文、测试数量、文件清单或代码。
5. 用户「批准交付」卡显示汇报和全部成员 PR；「批准合并」提供「部署」「发布预览版」「发布正式版」，各自仅在项目有 `kind=deploy`、`kind=preview`、`kind=release` 的流程时显示，默认都不勾。「暂不合并」须附原因并返回确认。批准后，若勾选发布但备注为空，先交主 Agent「写发布说明」，再进入「放行合并」；否则直接进入「放行合并」。由任务叫醒发起会话，不再单独通知选择。
6. 主 Agent 按顺序放行成员，被依赖的仓库在前：先放行提供被钉版本的包的成员的「待交付」，等合并并发布新版本；再退回钉这些包的仓库成员，让执行者更新钉定的包版本，经审查、检查回到待交付；最后放行依赖方成员。全部合并后备注写本项目最后一个合并提交，没有本仓库成员时写本项目当前目标分支提交。
7. 在该合并提交上按勾选依次调用 `run-workflows` 的 deploy、preview、release 三类，每类一次；每类调用项目的全部对应流程，预览和正式发布均传所选发布说明 `notes`；正式发布另传 `publish: "true"`。随后主 Agent 按 `goal` 走真实环境验证，选「通过」或附具体意见选「有问题」，用 `tell-session` 告知发起会话后结束。未勾部署时仍验证当前真实环境，备注说明未部署造成的未验证部分。

必填备注缺少时回原任务补填。成员快照、轮次和反馈保存在 `$CODA_ARTIFACTS/deliver.json`；运行之间只通过主 Agent 答复各自人工任务协调，不直接发消息。此流程不改变成员 develop 的审查、检查与合并路径。

测试在 `test/plugins/composer/`，用临时 Git 仓库及假的 coda-agent、gh 验证，不发真实 PR 或部署。PR 复用测试将实际脚本输出按引擎语义转换（`"true"` / `"false"` 转为布尔值），再用同版本 FEEL 求值真实 BPMN 网关条件，覆盖同提交复用、记录缺失与提交变化；check 包仅校验流程方言，此测试不运行完整 BPMN 引擎。设备验收段测试覆盖有无设备时的分流、占用范围、退出和重入路径。
