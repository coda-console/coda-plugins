# 输入框模式

`@coda-console/composer` 把输入框的五种模式放在同一个插件里，插件 ID 为 `composer`。

| 模式 | 入口 | 用途 |
| --- | --- | --- |
| 交接到新会话 | `/handoff` | 新会话承接当前上下文，共享工作目录；原会话保留，可继续使用。 |
| 子会话 | `/subagent` | 从任意会话启动子会话，承接近期上下文并沿用工作目录；可选完成后回报父会话或你。 |
| 执行命令 | `!` | 在会话工作目录执行命令，命令与结果作为消息发给 Agent；也可在新任务输入框使用。 |
| Ultra | `/ultra` | 主 Agent 负责决策、调度和验收，非微小任务交给 Coda 子会话；也可在新任务输入框使用。 |
| 循环 | `/loop` | 按周期把同一句话再发给 Agent，每轮做完才开始计时，7 天后自动结束；仅用于已有会话。 |

五个模式可同时开启，模式 ID 不变。Ultra 开启时，从这个输入框创建的新会话（包括子会话、交接和新任务）继承 Ultra 及当前子 Agent 名单，各自独立保留模式；关闭来源的 Ultra 不会关闭已创建会话的 Ultra。工具栏始终选择输入框自己的执行者；交接与子会话的参数另有可选 Agent，留空沿用输入框执行者。子会话也能创建自己的子会话。

3.0.0 按 [Coda #2063 的接口约定](https://github.com/coda-console/coda/issues/2063) 改为 `submissions` 协议参与者，依赖该 issue 第 2 步的后端支持，以及 [Coda #2085](https://github.com/coda-console/coda/pull/2085) 的新会话模式继承与实际投递计数，不能用于旧版回调宿主。交接、子会话和循环声明 `once: true`，发出的一条被收下后退出该模式；Ultra 保持开启，执行命令的触发词仍是 `!`。

插件只返回补充，不改正文、附件、引用或输入框的执行者。多个模式的补充由 Coda 合并，`tell` 是字符串数组，按列表追加后随这条发送到每个收到它的会话；只要有一项 `divert: true` 就不发给默认去向，各模式追加的去向仍分别执行。

| 模式 | 发出的一条的补充 |
| --- | --- |
| 交接 | `divert: true`，追加 `thread` 去向，带 `handoffSource`、可选 `agent`、`open: true` |
| 子会话 | `divert: true`，追加 `thread` 去向，带 `handoffSource`、`parentThreadId`、`replyTo`、可选 `agent`、`open: true` |
| Ultra | 首条、参数变化后的首条，以及创建新会话时返回完整开启说明；此后 `sent > 0 && sent % 10 === 0` 时返回仍在说明，其余返回 `null` |
| 循环 | `divert: true`，追加 `loop` 去向，带 `thread`、`every` |
| `!` | `divert: true`，会话中追加 `message` 去向，带 `thread`、`run: true`；新任务中追加 `thread` 去向，带 `run: true`、`open: true` |

新会话去向明确跳转，客户端按每项 `open` 执行。Coda 将非一次性、非触发式且适用于会话的模式和参数写入新会话输入框；各会话只为自己实际收到的模式消息计数，转发到新会话不增加来源的 `sent`。空 Agent 不写入目标，交由 Coda 沿用 `spec.agent`（包括 settings）。

## 循环用法

在已有会话的输入框里打 `/loop`，填写每轮要做的事，选择周期后点「开始循环」。周期默认 30 分钟，可选 5 分钟、10 分钟、15 分钟、30 分钟、1 小时、2 小时、3 小时、6 小时、12 小时或 1 天。

这条消息就是第 1 轮；Coda 收下后创建循环，输入框随即退出循环模式。每轮做完才开始计算下一个周期，不叠着跑；7 天后自动结束，也可提前停止，归档会话同样结束循环。计时与重发由 Coda 后端负责，会话进程被回收后仍会按时恢复。

循环的计时行为沿用 [Coda #2051](https://github.com/coda-console/coda/pull/2051)，3.0.0 通过上述 `loop` 去向提交。

## Ultra 模板设置改名

Ultra 的模板设置由 `ultra.templates` 改为 **`composer.templates`**，模板的数据结构不变。清单的预设只引用新设置名，由 Coda 按输入框所在目录读取。
旧 Ultra 包暂时保留，旧设置迁移和卸载旧插件由 [Coda issue #2050](https://github.com/coda-console/coda/issues/2050) 的第 4 步处理，本插件不自行迁移。

## Ultra 用法

输入框的 Ultra 协调模式（Coda 的[输入框模式](https://github.com/coda-console/coda/blob/main/docs/plugins.md#输入框模式)）：在保持质量的前提下，节省主 Agent 的 Token 和上下文。
主 Agent 负责定义任务、困难决策、调度和验收，非微小任务的主要执行工作按名单用 `spawn` 派给 Coda 子会话；关键路径和需要串行执行的任务也委派。
只有整个请求已经明确、简短答复或一次显然的局部操作就能完成时，主 Agent 才直接做，例如已知位置的错字或简单状态查询。
不能把复杂任务拆成单条命令逐个自己执行；小任务一旦需要排查或调试，就交给子会话。

输入框模式插件的 npm 包为 `@coda-console/composer`，分类「工作流程」。Ultra 的模式、参数和给 Agent 的话都在这个插件里。

**用法**：会话或新任务的输入框里打 `/ultra`（或在 `/` 菜单、iPhone 的「+」里选），输入框进入 Ultra；在新任务里进入，发出第一条后开出的会话就在 Ultra 里，点模式条打开参数：

| 参数 | 是什么 |
| --- | --- |
| 子 Agent 的预设 | `presets: { "from": "composer.templates", "by": "template" }`：Coda 按模板列首次出现的顺序分组。进入时填第一组，设置为空不填；选中一组只把名单填入一次，只取 `who`、`when`，之后可自由修改。没有单独的 `template` 参数，也没有切到「自定义」的回调 |
| 子 Agent | 名单，一行一个：Agent 组合（Agent、模型、推理强度、配置项）和「什么时候派给它」。名单为空或名单里没提到的活，Agent 用自己的 Agent 和模型派 |

单独开启 Ultra 时，消息照常发给这个会话；与其他模式一起开启时，按这些模式合并后的去向发送。点 × 退出 Ultra。

**告诉 Agent 什么**（`ultra.mjs`，经 Coda 的「顺带告诉」随下一轮带上）：

- 开着后发给本会话的第一条、参数改过之后的第一条，以及交接、创建子会话或默认去向创建新会话的消息：进入协调模式，原先「没要求就别派」不再适用；用户明确修改规则时优先，普通的实现请求不算解除协调职责。附上名单，一行一个，写成 `spawn` 要的 `agent`、`model`、`effort`、`mode`、`options`。
- 主 Agent 定义任务、处理困难决策、约定验收标准、选择执行者、检查证据并汇总。多文件修改、重构、调试、评审、详细规划、研究和验证默认委派；实现、编写测试、运行测试或构建及失败修复也交给子会话。微小任务例外按整个请求判断，为调度和验收做少量定向阅读、只读抽查可以。
- 子任务具体、自包含，给出相关背景、验收标准和不与其他执行中会话重叠的写入范围；相关工作交给同一个执行者，后续修正复用它。子会话回传简短结论、文件或来源、实际验证结果和未解决问题，不回传大量日志。
- 主 Agent 在交接任务里明确子会话是执行者，自己完成任务，不继承主会话的协调职责；没有明确指派就不继续转派，获准转派也走 Coda。结果自动回来，主 Agent 不重复子会话的搜索、修改和常规检查。
- 委派只走 Coda 的 `spawn`，即使用自己的 Agent 和模型，也创建 Coda 子会话；除非用户明确要求，不用运行时自带的子 Agent 或委派工具。
- 之后每收下 10 条，在下一条模式内消息带简短提醒（`sent` 为 10、20、30……）：节省主 Agent 的 Token，非微小执行工作必须委派，串行和关键路径也适用，不能拆成单条命令自己做或重复子会话的工作；也提醒执行者分工、等待和只走 Coda 的规则。
- 名单写得太长、连同说明超过 Coda 一次能告诉 Agent 的长度（4000 字）时，那条消息发不出去，界面说明原因；改短后再发就照常告诉。
- 插件声明 `activationEvents: ["onStartupFinished"]`，后端或插件宿主重启后即加载并恢复观察，不需要先发送新消息。插件通过 `coda.watch('composers', …)` 记住上次看到的对象；Ultra 从某会话的 `spec.modes` 消失且此前 `sent > 0` 时，用 `coda.tell` 告知关闭。退出时撤销 Ultra 的优先委派职责和「委派只走 Coda」限定，恢复通常的执行与委派指令，Coda 子会话回到「有要求才派」；一条都没发过就不说。

同时在跑的子会话有多少由 Coda 管（「会话生命周期」插件的设置「同时执行的子会话」），满了 `spawn` 当场失败。
并发已满时等已有 Coda 子会话结束、腾出名额；`spawn` 不可用时说明阻塞，只继续不依赖它的协调工作。两种情况都不扩大微小任务例外或改用原生子 Agent。
这些职责和委派渠道仍是提示词约束，插件没有在运行时禁用主 Agent 的执行工具或原生子 Agent 工具。

**设置** `composer.templates`：一列行，每行「模板名、Agent、什么时候派给它」，同一个模板名的几行是一个模板。默认不带模板，子会话沿用当前会话的 Agent 和模型；用户可以自行添加、修改、删除模板。

测试在 `test/plugins/composer/`。

委派范围与微小任务例外的基础文案采用 [oh-my-claudecode 的委派规则](https://github.com/Yeachan-Heo/oh-my-claudecode/blob/82602887b71a3984e040fac2839ec8d27a7c67b6/docs/CLAUDE.md#L16)，
