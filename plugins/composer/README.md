# 输入框模式

`@coda-console/composer` 把输入框的五种模式放在同一个插件里，插件 ID 为 `composer`；另带两个开发流程：监督开发（`develop`，一个需求一条需求分支）与需求交付（`deliver`），以及监督开发里主 Agent 往需求分支提改动用的「块」（`piece`）。开发流程由你在输入框「＋」里开启，或由 Agent 用 `workflow_run` 带 `confirm: true` 填好、你在开工卡上确认（Coda 的开工卡）。

| 模式 | 入口 | 用途 |
| --- | --- | --- |
| 交接到新会话 | `/handoff` | 新会话承接当前上下文，共享工作目录；原会话保留，可继续使用。 |
| 子会话 | `/subagent` | 从任意会话启动子会话，承接近期上下文并沿用工作目录；可选完成后回报父会话或你。 |
| 执行命令 | `!` | 在会话工作目录执行命令，命令与结果作为消息发给 Agent；也可在新任务输入框使用。 |
| Ultra | `/ultra` | 主 Agent 定任务、做决定、审查，不改代码的调研与核实按任务交给名单里的执行者；也可在新任务输入框使用。 |
| 循环 | `/loop` | 按周期把同一句话再发给 Agent，每轮做完才开始计时，7 天后自动结束；仅用于已有会话。 |

五个模式可同时开启，模式 ID 不变。Ultra 开启时，从这个输入框创建的新会话（包括子会话、交接和新任务）继承 Ultra 及当前子 Agent 名单，各自独立保留模式；关闭来源的 Ultra 不会关闭已创建会话的 Ultra。工具栏始终选择输入框自己的执行者；交接与子会话的参数另有可选 Agent，留空沿用输入框执行者。子会话也能创建自己的子会话。

11.1.0 修监督开发验收段拿锁顺序会让两条需求互相等死的问题（11-18 实际发生过：一条运行只占了组、它发起的安装在等测试机，另一条占着测试机在等这个组）：改成先占 `hold` 的组、再占 `device` 的设备，两把锁都带 `borrow="no"`。约定（composer 不加机制强制，详见「设备占用」）：`hold` 只填一个环境组，比如项目给需求分支专用的后端部署组；不要填别的设备的组，设备用 `device` 填；也不要填 `host` 这类构建名额组，填错了可能卡住。安装要用的、会和别的需求共用的环境组要填进 `hold`，顺序保证以此为前提。`borrow="no"` 只保证本段自己的申请独立排队，宿主按会话认出借方，同一会话发起的其他运行仍可能借到。原地恢复时宿主会把这一段占过的锁一次全部重排，罕见情况下仍可能互相等住，这次不处理。需求交付（`deliver`）没有 `hold`，它的安装要用别的需求作为 `hold` 占着的共用组时，仍可能互相等住。同一版本新增挂点 `abandoned`：两条放弃路径结束前先运行加入它的流程，传 `run`、`branch`，不出卡、加入者全跑、失败则运行失败，项目在这里收回需求占着的东西。

12.0.0 块（`piece`）收成「写的人自验、机器检查、一位评审者、主 Agent 取舍」的形态（下文「块」）：输入去掉 `reviewer2`、`autoLandMinor`（引擎拒收流程没声明的参数，带它们的旧调用会失败），输出去掉 `autoLanded`、`summary`；评审只调一次 `review-commit`，评审结论不再决定去向：去掉「分流评审意见」「执行者处理评审意见」「整理收敛经过」的回路和小改动免审（`scripts/minor.mjs`、`triage.mjs` 的 `triage`）。审查卡改成一页结论：执行者最后一条回复（固定说明要求以「交付说明」开头给完成标准逐条和怎么验的两段）、项目检查、评审结论（必须修逐条，小问题、原有问题只给条数）、改动范围（与监督开发的「改动区域」同一份算法）、看改动的命令；说明改为不要求读 diff、只有必须修才退回。主 Agent 退回后评审者只复评之后的变动，带上没关的必须修和历次退回意见；同一块退回满三次后再退回出你的卡「这一块三轮没过」。监督开发派块不再传 `reviewer2`、`autoLandMinor`，「需求进行中」不再写免审合入。需要 review 插件 4.0.0 及以上；不兼容在跑的块运行，升级前先让它们跑完或取消。

12.0.0 还把监督开发（`develop`）收成同一形态（下文「监督开发」「整体评审」）：输入去掉 `reviewer2`、`reviewer3`、`autoLandMinor`，加 `overallReviewer`「整体评审者」，`reviewer` 只评每一块；「需求进行中」的人选和派块备注里能换的只有执行者、备用执行者、评审者。提交验收依次是跟上目标分支、开或更新 PR、项目检查、整体评审、设备验收、合并前检查、GitHub 检查，最后待交付、批准或自动合并，合并前检查只对最终要合并的提交跑。整体评审由 `overallReviewer` 一位调一次 `review-commit` 评整条需求分支，一次运行只评一次：这次运行还没评过才评，只合进了一块（跟上目标分支的块不算）且它评成过时跳过，「提交验收」加勾选项「重新整体评审」。没有必须修就往下走，小问题、原有问题写进 PR 描述和汇总；有必须修或没评成交主 Agent「整体评审结论」，卡上是一页结论。整体评审不再交执行者修、不再增量复评，`scripts/triage.mjs` 删掉。`autoMerge` 开着时合并前检查和 GitHub 检查通过就直接合并，这次运行一次都没评成过或整体评审出过必须修时照常出批准卡。「需求进行中」「整体评审结论」和块的审查卡写同一套取舍标准：只有必须修才修，修复块只修那一条；必须修的说法同 review 4.0.0 的 `rules.md`（含会扩散的结构问题和会偶发失败的测试）。需求交付为成员开工时一并选评审者和整体评审者。不兼容在跑的需求运行，升级前先让它们跑完或取消。

12.1.0 监督开发与块的收尾五处：①监督开发结束时的输出多一个 `afterMerge`，写明合并后流程的结果（同 review 4.1.0 简易开发的 `afterMerge`，措辞一致）：勾了的都成功是「合并后的流程已全部结束，不用再等：部署：成功；…」（名字是批准卡上勾选项的名字，拿不到用流程名），没跑任何合并后流程的各条路（没勾、补填时都选了不跑、归属需求交付、自动合并）是「没有运行合并后的流程，没有什么要再等的」；有一项没成功时运行失败，错误里写明是哪一项，这条路不变。②单块需求勾「重新整体评审」现在生效：勾了就当没评过，只合进一块且它评成过也照常评一次。③块换备用执行者、让执行者合并需求分支（审查卡上选的和合入时试合并冲突交回的）之后，到有一次完整评审评成为止都按完整评审算，不再在完整评审没评成、主 Agent 又退回时拿换人或合并之前评过的提交当复评起点、带着之前的发现。④复评没评成（评审没完成或调用没成）时，审查卡仍列出上一轮还开着的必须修，注明这一轮没有重新核实。⑤附给评审者的任务书里，主 Agent 定了不改的条目另列标题和位置，评审者不再只看到编号。块的审查卡上复评坚持的必须修后面带评审者给的理由（「现在的代码还缺」，来自 review 4.1.0 的 `resolutions[].reason`），需要 review 插件 4.1.0 及以上。

插件只返回补充，不改正文、附件、引用或输入框的执行者。多个模式的补充由 Coda 合并，`tell` 是字符串数组，按列表追加后随这条发送到每个收到它的会话；只要有一项 `divert: true` 就不发给默认去向，各模式追加的去向仍分别执行。

| 模式 | 发出的一条的补充 |
| --- | --- |
| 交接 | `divert: true`，追加 `thread` 去向，带 `handoffSource`、可选 `agent`、`open: true` |
| 子会话 | `divert: true`，追加 `thread` 去向，带 `handoffSource`、`parentThreadId`、`replyTo`、可选 `agent`、`open: true` |
| Ultra | 创建新会话（交接、子会话、默认去向为新会话）时返回完整开启说明；已有会话里，仅当状态标记要给完整说明（首次、改名单）时返回，其余返回 `null`；压缩后的说明由 watch 立即给（见「Ultra 用法」） |
| 循环 | `divert: true`，追加 `loop` 去向，带 `thread`、`every` |
| `!` | `divert: true`，会话中追加 `message` 去向，带 `thread`、`run: true`；新任务中追加 `thread` 去向，带 `run: true`、`open: true` |

新会话去向明确跳转，客户端按每项 `open` 执行。Coda 将非一次性、非触发式且适用于会话的模式和参数写入新会话输入框；各会话只为自己实际收到的模式消息计数，转发到新会话不增加来源的 `sent`。空 Agent 不写入目标，交由 Coda 沿用 `spec.agent`（包括 settings）。

## 循环用法

在已有会话的输入框里打 `/loop`，填写每轮要做的事，选择周期后点「开始循环」。周期默认 30 分钟，可选 5 分钟、10 分钟、15 分钟、30 分钟、1 小时、2 小时、3 小时、6 小时、12 小时或 1 天。

这条消息就是第 1 轮；Coda 收下后创建循环，输入框随即退出循环模式。每轮做完才开始计算下一个周期，不叠着跑；7 天后自动结束，也可提前停止，归档会话同样结束循环。计时与重发由 Coda 后端负责，会话进程被回收后仍会按时恢复。

循环的计时行为沿用 [Coda #2051](https://github.com/coda-console/coda/pull/2051)，3.0.0 通过上述 `loop` 去向提交。

## Ultra 模板设置改名

Ultra 的模板设置由 `ultra.templates` 改为 **`composer.templates`**，模板的数据结构不变。清单的预设只引用新设置名，由 Coda 按输入框所在目录读取。
旧 Ultra 包暂时保留，旧设置迁移和卸载旧插件由 [Coda issue #2050](https://github.com/coda-console/coda/issues/2050) 的第 4 步处理，本插件不自行迁移。

## Ultra 用法

在会话或新任务输入框打 `/ultra`，点模式条选择执行者名单；点 × 退出。单独开启时消息照常发给当前会话，与其他模式一起开启时按各模式的去向发送。
Ultra 只管派活：主 Agent 定任务、处理困难决策、审查别人交回的东西；不改代码的调研、排查和核实用 Coda 的 `spawn` 交给名单里的执行者，按任务挑。
它不规定代码怎么改、走不走开发流程：开发流程由你在输入框「＋」里开启，或由 Agent 用 `workflow_run` 带 `confirm: true` 填好、你在开工卡上确认，它的规则写在交给主 Agent 的任务里。

`composer.templates` 是执行者模板，一行「模板名、Agent、什么时候派给它」。同一模板名的行是一组，进入时填第一组；默认没有模板。
Ultra 参数仍保存为 `subagents`，预设引用 `{ "from": "composer.templates", "by": "template" }`，选择预设只填入名单一次，之后可修改。
派活时任务书要自成一体：目标与它服务的决定、已知或已排除的、范围与不要碰的、去哪里找、交回什么（先结论，再来源和实际证据）。
结果不好时按原因处理：任务书漏了的，补写后发回同一会话；只有说法没有证据的，向同一会话要证据；任务书清楚但结果不对的，换名单里的另一项；会话中断或工具失败的，重试；不要自己悄悄重做。
名单管所有为委派的工作选 Agent 的地方：Coda `spawn`，以及流程里要 Agent 的输入，都按任务从名单选，传 `agent`、`model`、`effort`、`mode`、`options`；只有名单为空或没有条目适合时，才用当前会话的 Agent 和模型。提示不点名具体流程和输入，也不讲开发流程怎么走。

会话输入框开着 Ultra 时，完整说明只在下列情况给一次，平时不发提醒：

- 首次生效、名单改过：输入框的变化只更新插件内存里的状态（名单、`sent`、`compactions`、是否要给完整说明），不 `tell`，免得用户在界面上改名单时连发。说明随下一条用户消息（`coda/submission@1` 参与者，已有会话里返回完整说明并清掉标记，否则返回 `null`；创建新会话时照旧返回完整说明）或下一轮结束（`coda.watch('threads')` 里 `turn` 由非空变 `null`，用 `coda.tell` 追加）给出，两处只会给一份。空闲时连着改几次只给最新名单的一份。
- 压缩：`coda/composer@1` 的 `status.compactions`（非负整数，缺省按 0 计）变大就是压缩，每次压缩加 1；插件立即用 `coda.tell` 给完整说明，不等一轮结束或下一条消息，不论当时是否在跑一轮，并清掉待给标记。两次压缩之间没有用户消息（`sent` 一直是 0）也都识别。只看 `compactions`，不从 `sent` 由大于 0 变 0、内容或用量推断。

怎么认新会话：带着 Ultra 新建的会话，输入框与第一条在同一个事务里写成 `sent=1`，第一条已带完整说明；刚进入 Ultra 时 `sent=0`，给完整说明；插件重启后重放的输入框当作首次（重启后会多给一次），`compactions` 只记基线，不算压缩。
新任务输入框（`new:…`）本身不发说明，它创建的会话照上面处理；未开 Ultra 的会话不发。状态只放内存。

6.2.0 起 Ultra 每轮提醒（原来按用户发出的消息每 10 条一次，长程任务里会话多半被流程结果叫醒，计数不动，压缩后名单也丢了）；10.3.0 起去掉每轮提醒，改为只在首次、改名单和压缩后给完整说明，压缩由 `status.compactions` 识别。
并发已满就等名额；spawn 不可用就报告阻塞，不改用原生子 Agent。用户的明确指令优先。
5.0.0 起 Ultra 不再要求「所有代码修改都通过 develop」，也不再讲 develop、deliver 的用法；两个流程改为由你在会话里开启，或由 Agent 发起「开工」后你在开工卡上确认，develop 的执行者从 `agent`、`model`、`effort`、`mode` 四个参数换成一个 `executor`（Coda #2303）。需要支持流程参数 `agent` 类型（协议 3.5.0，Coda #2332）、`coda:wake` 与 `note="required"` 的 Coda，不能用于旧版。

插件声明 `activationEvents: ["onStartupFinished"]`，重启后通过 `coda.watch('threads', …)` 与 `coda.watch('coda/composer@1', …)` 恢复观察。
Ultra 消失时，若这个会话收到过说明（submission 投递过或 watch 告诉过；重启后不知道时按 `sent > 0` 判断）就用 `coda.tell` 告知关闭一次，恢复通常的执行与委派规则；没收到过就不说。
名单连同说明超过 Coda 单次告诉 Agent 的 4000 字上限时，缩短名单再发。这些分工是提示词约束，不在运行时禁用工具。

## 监督开发

一个需求开一次「监督开发」（`develop`），对应一条需求分支 `req/<运行 ID>`。和主 Agent 把需求聊清楚后，在输入框「＋」里开启它，或由 Agent 用 `workflow_run` 带 `confirm: true` 填好、你在开工卡上确认。
中间的事都由主 Agent 负责：它在「需求进行中」一块块派「块」（`piece`，见下一节），交给执行者，每一块经项目检查、评审和它的审查后合进需求分支，这期间不找你；
它判断需求做完后「提交验收」，需求分支先跟上目标分支，才开 PR 进目标分支，经项目检查、整体评审（一次运行一次）、设备验收、合并前检查和 GitHub 检查后，由你批准一次，用合并提交合并，再运行你勾的合并后流程。
它是手动流程，不订阅 PR 事件，也不依赖 review 插件（评审按名字调用能力 `review-commit`）；它开的 PR 不会启动 PR 生命流程（见下文「不触发 PR 生命流程」）。

| 输入 | 用途 |
| --- | --- |
| `title` | 需求名（也是 PR 标题），默认空。目标与完成标准是发起时带的需求文字（`run.message`：「＋」或开工卡上的需求、`workflow_run` 的 `message`）；需求名和它缺一样时由主 Agent 写 |
| `devices` | 布尔值「设备验收」，默认关；改了客户端、要在 Mac 或 iPhone 上验收时打开 |
| `device` | 可选文本「验收设备」，如 `duo-testbed`，默认空；开启设备验收且非空时，从安装前到验收结束独占这台设备；留空不占设备 |
| `hold` | 可选文本「验收时占用」，一个组名，默认空；开启设备验收且非空时，安装与验收期间另外占着这个组（容量 1），如项目给需求分支专用的后端部署组；留空不占。只填一个环境组，不要填别的设备的组或 `host` 这类构建名额组（见「设备占用」） |
| `delivery` | 字符串「所属需求交付」，填需求交付（`deliver`）运行的 ID；默认空，为独立交付 |
| `executor`、`executor2`、`reviewer` | 「执行者」「备用执行者」「评审者」，各是一组 Agent 选择（流程参数的 `agent` 类型），没有默认值，不填就是空（`null`）；是每一块的默认人选（下文「派块」），主 Agent 派块时可在备注里换。`executor` 还负责提交验收时跟上目标分支的解冲突，不填时每一块都要在备注里写执行者；`reviewer` 不填，块就不评 |
| `overallReviewer` | 「整体评审者」，一组 Agent 选择，没有默认值，不填就不整体评审；提交验收时评一次整条需求分支，见下文「整体评审」 |
| `autoMerge` | 布尔值「检查和评审通过后自动合并」，默认关。开了时合并前检查和 GitHub 检查通过（开了设备验收的也已验收通过）就不出批准卡、直接合并，合并后的流程不自动跑，结束照常叫醒发起会话；这次运行一次都没评成过（整体评审和块的评审都没有）或整体评审出过必须修时照常出批准卡，需求交付的成员（`delivery` 非空）照常进「待交付」。判定只在「整理整体评审」输出的 `auto` |
| `base` | 「目标分支」，留空从 GitHub 读取仓库默认分支 |

0. 需求名（`title`）和需求文字（`run.message`）缺一样时（如你直接在会话里开启的），先交主 Agent「写需求」：这张任务不叫醒它（`coda:wake="false"`），随你在会话里的下一条消息告诉它，说明你开启了监督开发、它要做什么；发起时带了需求文字就一并写在任务里。两样都有时（如开工卡确认的、需求交付发起的）不经过这张任务。主 Agent 答复时备注必填：第一行是需求名，空一行后是目标与完成标准；缺一样回到这张任务。
1. **建需求分支**：从远端目标分支的最新提交建 `req/<运行 ID>` 并推送，分支名只用 ASCII。远端已有同名需求分支时沿用它，不重建：运行从头重跑时不会因为分支已存在而失败，也不会丢掉已合进需求分支的改动。
2. **需求进行中**：交主 Agent 一张「需求进行中」任务，可以挂好几天。任务里写着需求、目标、需求分支，以及怎么推进：
   - 每一块选「派一块」，写清标题与任务书；跟上目标分支选「跟上目标分支」（下文「派块」）；
   - 一次只派一块：派出后等它结束才回到「需求进行中」，有依赖的按先后派；
   - 中途想先看效果，可以用需求分支的提交发起 `mac-preview-install`、`ios-preview-install`，或对需求分支 head 跑一次合并前检查（加入挂点 `premerge` 的流程）。

   答复有五种：
   - 「派一块」：备注必填，第一行是这一块的标题，其余是任务书；最前面可以写换人的行。派出一块，结束后回到「需求进行中」。
   - 「跟上目标分支」：备注可不写，写了附在固定任务后面。派一个 `sync=true` 的块，结束后回到「需求进行中」。
   - 「提交验收」：备注必填，是写给你的改动汇报（做了什么、需要你知道的风险或没做的），放在批准卡和 PR 描述最上面，每次提交以最新一份为准；进入收尾。
   - 「暂停」：备注必填，写为什么停、等什么。转成你手上的「需求已暂停」卡，卡上是这段备注；你选「继续」回到「需求进行中」（附言随原因交给主 Agent），选「放弃」结束。这样主 Agent 不会每次空下来又被叫醒。
   - 「放弃」：结束这次运行，需求分支保留。

   必填备注没写（含只写空白）、派块的写法看不懂时回到同一张任务说明缺什么，不派。每次回到「需求进行中」，任务里都写着回来的原因：刚合进需求分支的块（提交与块的运行）、没正常结束的块、检查失败的运行与步骤、设备验收的意见与截图路径、你暂不合并的原因、整体评审后主 Agent 的说明与那一页结论等；主 Agent 派修复用的块，再重新「提交验收」。

   「提交验收」带一个勾选项「重新整体评审」，默认不勾，只在填了 `overallReviewer` 时给出：这次运行已经整体评审过，勾了这一次就当没评过，照常评一次（下文「整体评审」）。

   任务里写着取舍标准，和块的审查卡、「整体评审结论」是同一套说法：只有必须修才派块修，评审者说成立不等于现在要修；必须修是合并后用户会遇到错的结果、丢数据、安全问题，对外契约写错，测试是红的或会偶发失败，漏了任务书要求的事或做了任务书之外的事，以及会扩散、越晚越难改的结构问题（跨模块或会被照着写：绕过已有边界、依赖方向反过来、第二个事实来源或第二套做同一件事的机制、迁移只做一半），其余是小问题；修复块只修那一条，不顺手带小问题，不加设计改动，不把以后的需求提前做进来。
3. **跟上目标分支**：先让需求分支跟上目标分支（下文「提交验收时跟上目标分支」），有冲突且没填开工执行者、或推送被拒时带着原因回到「需求进行中」。
   **开 PR**：开或更新需求分支进目标分支的 PR，标题是需求名。正文依次是主 Agent 最近一次「提交验收」的汇报、合进需求分支的块列表（目标分支最新提交到需求分支 head 之间，按先后：说明带 `Coda-Piece: <运行 ID>` 的块合入提交，不论在哪条父链上，附上那次运行的链接；再加 first-parent 上没带它的提交，如跟上目标分支的块的合并提交；去掉下面流程直接推的）、流程直接推到需求分支的提交（跟上目标分支的合并提交和执行者解冲突的提交，有才列）、改动区域统计（下文「改动区域」），合称汇总，批准卡和待交付卡贴的就是它（整体评审评过、有小问题或原有问题时，「整理整体评审」再加上它们）。
   块列表从需求分支的历史读，块不开 PR；已开着的 PR 用 `gh pr list --head req/<运行 ID> --state open` 从 GitHub 找。需求跨好几天，从头重跑时只重建收尾，不靠运行暂存；唯一保留的是 `develop.json` 里流程直接推送的记录（`pushed`），否则这些提交会被错列成块。
4. **项目检查**：独立交付开了设备验收（`devices=true`、`delivery` 留空）时，开 PR 后与检查并行调用项目加入挂点 `prebuild` 的（预编）流程，传需求分支 head，填了 `device` 时另传 `device`；它为随后验收要装的客户端先编好，检查不等它，它失败只留在调用记录里，安装流程到时照常自己构建，项目没有这类流程时立即结束。项目检查已在各块上跑过；需求分支 head 是本运行已通过检查的同一提交时复用，否则在它上面跑一次挂点 `check`。失败带着运行链接回到「需求进行中」，主 Agent 用 `workflow_status` 读失败的流程、步骤和日志。
5. **整体评审**：项目检查有了结论，「定整体评审」决定这次评不评，评了的有必须修或没评成交主 Agent「整体评审结论」，否则往下走（下文「整体评审」）。
6. **设备验收**：`devices=true` 且 `delivery` 留空时进入「安装与设备验收」段。主 Agent 用 `workflow_run` 带需求分支 head 的精确 `commit` 只安装改到的那一端（`mac-preview-install`、`ios-preview-install`），发起的安装都成功后答复「已装好」；要先修改时选「回到进行中」，备注必填，缺少时返回安装卡。随后你答复「设备验收」，「不行」必须附言（写意见或附截图，`note="required"`），意见与截图路径带回「需求进行中」。改了后端、项目允许从需求分支部署后端时，主 Agent 按项目的说明同样带需求分支 head 发起后端部署；填了 `hold` 时本段占着那个组（下文「设备占用」）。验收通过后流程用 `tell-session` 告诉主 Agent 接下来跑合并前检查与 GitHub 检查，通过后进需求交付验收、自动合并（见第 8 步）或等你批准。
7. **合并前检查与 GitHub 检查**：整体评审和设备验收之后需求分支 head 不再变，在它上面跑一次挂点 `premerge`（合并前检查，放每个版本都跑嫌贵的验证），再等 GitHub 检查：核对 PR 的 `headRefOid` 与需求分支 head 一致，每 10 秒查询一次检查，最多等 120 秒登记；出现检查后用 `gh pr checks <PR> --watch` 等全部结束，并再次核对 head。连续 120 秒为空才按无 CI 通过，日志明确记录这一判断（有界等待是为了兼容 GitHub Actions 和外部 CI，不猜测 workflow 的事件、路径或分支过滤；超过窗口才登记的 CI 不在保证范围内）。所以待交付、批准卡和自动合并之前，合并前检查与 GitHub 必需检查都已通过。任一项失败带着运行链接回到「需求进行中」。
8. **批准**：`delivery` 非空时进入给主 Agent 的「待交付」（见下文），不出你的批准卡。开了 `autoMerge`、这次运行评成过且整体评审没出过必须修时也不出批准卡，直接合并（见上文输入表）。否则先在需求分支 head 上列出加入挂点 `merged` 的流程（`hook-joiners`），你在「批准合并」卡上决定：卡上只有汇总（整体评审的小问题、原有问题在里面）、已通过的检查（含设备验收，评过的写明整条需求分支已整体评审）和 PR；「合并」的勾选项是这些流程（下文「合并后的流程」），之后是「全部完成后通知 Agent」，默认勾选。「暂不合并」必须附言，原因带回「需求进行中」交给主 Agent 跟进。批准后直接合并，不再跑检查。
9. **合并**：用合并提交合并：`gh pr merge --repo <host/owner/repo> --merge --match-head-commit <需求分支 head> --delete-branch`。目标分支的 first-parent 历史里每个需求一个提交（按 first-parent 计数的构建号照常算），需求分支里每个块一个提交，可以二分、可以单独回退。
   合并前查询 PR 状态：已合并且 head 与本次记录一致时直接输出原合并提交；已合并但 head 不一致或已关闭未合并时明确报错。合并命令失败后查询一次 PR，仅在仍 OPEN 且 `mergeable=CONFLICTING` 时带着原因回到「需求进行中」：主 Agent 选「跟上目标分支」派一块，把最新目标分支合进来、解冲突、顺延撞号的迁移版本，再提交验收；之后重新跑检查、出新的批准卡，合并后的流程以新卡为准。其余合并失败保留原退出码，不依赖错误文案判断冲突。仓库从 PR URL 取得，gh 只删除远端需求分支、不操作本地分支，支持分离 HEAD 检出，也兼容 GitHub 合并后自动删除分支。
   成功后运行你勾的合并后流程（下文「合并后的流程」）；一个都没勾，或勾了的都被选了「这一项这次不跑」，就结束。结束时交给发起会话的消息里有输出 `afterMerge`，写明合并后流程的结果（下文「合并后的流程」）。

「全部完成后通知 Agent」控制最外层结束事件的 `coda:notify`：取消勾选后，合并及所选合并后流程全部成功时不叫醒发起会话，只在下一轮顺带告知结果；失败仍叫醒。依赖 Coda #2107 的结束通知支持。

`delivery` 非空时（成员需求运行，由需求交付发起），项目检查、整体评审、合并前检查与 GitHub 检查之后进入给主 Agent 的「待交付」，跳过安装和设备验收，不受 `devices` 影响。任务列出所属需求交付、PR、head、需求分支和汇总：

- 「退回修改」备注必填，缺少则返回待交付；意见带回「需求进行中」，派一块修好后重新提交验收、跑检查，再回到待交付。
- 「放行合并」由主 Agent 按需求交付运行的顺序选择，随后以合并提交合并（合并前检查已在待交付前跑过）；合并成功输出合并提交并结束，仍通知发起会话，不运行合并后的流程（由需求交付统一运行）。

运行之间只通过主 Agent 答复各自的人工任务协调，不直接发消息，也不依赖跨仓库原生子运行。反馈与汇报暂存于 `$CODA_ARTIFACTS/develop.json`；长期结果在需求分支、块与进目标分支的 PR 里。

### 派块

主 Agent 在「需求进行中」选「派一块」或「跟上目标分支」时，需求运行用 `callActivity` 调用块（`piece`）：`branch` 是需求分支，`base` 是目标分支，`title`、`task`、`sync` 来自答复。
块是需求运行的子运行：运行页「调用的流程」列出每一块；取消需求运行时，正在跑的块一起停。块里的「主 Agent 审查」等人工任务照旧交给发起需求的主 Agent 会话：Coda 按名字调用时，被调运行属于调用方运行所属的会话。
块一次只派一个：派出后需求运行停在这一步，等块结束才回到「需求进行中」。

- 「派一块」：备注第一行是标题（也是合进需求分支那个提交的标题），其余是任务书（背景、范围、验收要求），两样都要有。
- 「跟上目标分支」：标题是「跟上 <目标分支>」，任务固定，备注写了附在后面，`sync=true`（下文「跟上目标分支」）。

人选默认取开工单：执行者、备用执行者是 `executor`、`executor2`，评审者是 `reviewer`；整体评审者 `overallReviewer` 不评块。「需求进行中」按下面的写法列出这三位的开工值。
要换人就在备注最前面写换人的行，一行一个角色（可带 Markdown 列表的 `- `），没写的角色照旧：

```text
- 执行者：<Agent ID>，模型 <模型>，强度 <强度>，模式 <模式>
- 评审者：无

修好登录跳转
## 背景
……
```

- 角色只认执行者、备用执行者、评审者，冒号全角半角都行。
- 冒号后先写 Agent ID，再按需写「模型 …」「强度 …」「模式 …」，各一次、逗号隔开；没写的用 Agent 的默认值。写了就整组换掉开工值，开工值的其他选项不带过来。
- 备用执行者和评审者写「无」，表示这一块不用。两种答复都先读这些行。

「读取进行中的答复」把这些行解析成标量（每个角色的 Agent ID 或「无」，以及模型、强度、模式），`callActivity` 的参数用 FEEL 的 `context merge` 拼成 agent 对象，没写的设置不带键；角色没写就原样传开工值。
写法看不懂（不认的设置、角色写了两次、执行者写「无」、Agent ID 不合规）、标题或任务书缺一样、开工没填执行者备注里也没写时不派，带着原因回到「需求进行中」，之前回来的原因保留。

块合进需求分支时（块输出 `commit`、`run`、`reviewed`），下一次「需求进行中」写上刚合进的提交和块的运行。
块失败、被取消或主 Agent 在块里选了放弃时，`callActivity` 的出错边界接住，带着原因回到「需求进行中」，需求运行本身不失败。Coda 不把被调运行的错误交给边界之后的步骤，所以原因写的是哪一块没正常结束、去本运行的步骤「块」看它调用的块运行。合入状态也不能断言：块合入时先推需求分支、再删临时分支，删除失败时块失败但提交已经合进去了，所以原因要主 Agent 先看需求分支里有没有这一块（说明带 `Coda-Piece: <块运行 ID>`，跟上目标分支的块是执行者的合并提交），确认没合进才重新派。

### 挂点

监督开发与块调用的项目流程都按挂点找（Coda 的 `docs/workflows.md`「调用其他流程」），本插件不认识任何一类。每个挂点分两项写：**运行提交**是被调的流程跑在哪个提交上，由 `run-workflows` 的 `commit` 决定，不是输入；**传入的输入**是 `inputs` 里实际有哪些字段。加入者不要把运行提交声明成输入。

| 挂点 | 谁调用 | 怎么跑 | 运行提交 | 传入的输入 |
| --- | --- | --- | --- | --- |
| `check` | 块每次交付、监督开发提交验收（需求分支 head 没通过过时） | 全部运行并等结束，有一个失败就算没通过 | 块交付的提交；提交验收时是需求分支 head | 无 |
| `premerge` | 监督开发提交验收，整体评审与设备验收之后、待交付或批准卡之前 | 同上 | 需求分支 head | 无 |
| `prebuild` | 监督开发提交验收，独立交付开了设备验收时 | 全部运行，不等、不管成败 | 需求分支 head | 可选 `device`（填了时） |
| `merged` | 批准卡（下文「合并后的流程」） | 只跑勾了的 | 合并提交 | 批准时填写或合并后补齐的文字，每个加入者只收到自己声明的输入 |
| `abandoned` | 监督开发放弃时（下文「放弃后的流程」） | 全部运行，不出卡；失败则运行失败 | 本次运行的提交（放弃时没有合并提交） | `run`（本次需求运行的 ID）、`branch`（需求分支） |

`develop` 自己加入挂点 `develop`：Coda 在「＋」和开工卡上列出加入这个挂点的流程作为开发流程。

### 合并后的流程

监督开发与需求交付声明挂点 `merged`：合并后要做的事（部署、发布预览版、发布正式版……）不写在流程里，由项目自己的流程（或启用插件的流程）用 `<coda:join hook="merged" …/>` 加入（Coda 的 `docs/workflows.md`「调用其他流程」）。约定：

- **加入者带什么**：`name` 是卡上勾选项的名字（不写用流程名），`detail` 一行说明，`default` 是否默认勾（不写为不勾，默认不勾就由加入者这样表达），`order` 排序（小的在前，不写排最后），可选 `inputs`：它要从卡上拿的自己的文字参数（本流程 `type` 为 string 的 `coda:input`，标签取参数的 `label`），如发布说明 `notes`。
- **卡上**：批准前用 `hook-joiners`（`hook=merged`，`commit` 是要批准的 head）列出加入者，作为「合并」的勾选项（`coda:optionList`），你可以勾任意几个；勾上带 `inputs` 的加入者时卡上出现对应的输入框（几项要同一个输入只出一个）。
- **合并后**：在合并提交上用 `run-workflows`（`hook=merged`，`only` 是勾了的流程名，`commit` 是合并提交，`inputs` 是卡上写了的文字）运行勾了的，等它们都结束；一个没成功这一步就失败。每个加入者只拿到它自己声明的参数。没勾任何一个就不调用。
- **卡上没写的文字**：勾了的加入者要、卡上没写的输入，合并后先交主 Agent「填写合并后流程要的文字」，每个输入一张（依次），任务里写明是哪一项、哪几个流程要；主 Agent 按这次合并进来的改动写面向用户的文字，「已写好」的备注必填（`note="required"`），只附文件没写字时「整理合并后流程的参数」失败并写明是哪一项。选「这一项这次不跑」（备注可不写）是这段文字不写：「整理合并后流程的参数」把所有勾了且要这段文字的加入者（几个加入者共用一段文字，如预览发布与正式发布都要 `notes`，就全部）从 `only` 里去掉，输出新的 `only` 交给 `run-workflows`，其余勾了的照常运行；新的 `only` 为空就不调用 `run-workflows`，监督开发直接结束，需求交付直接进入真实环境验证。
- 成员需求运行（`delivery` 非空）不列出、不运行，由需求交付统一运行。
- **结束时的结果**：监督开发结束事件的输出 `afterMerge` 让只看发起会话那条消息的人知道合并后的流程已经全部结束、不用再等。都成功时是「合并后的流程已全部结束，不用再等：部署：成功；发布预览版：成功」（「记下合并后流程的结果」`after-run` 写，名字是卡上勾选项的名字，拿不到用流程名）；没跑任何合并后流程的各条路（没勾、补填时都选了「这一项这次不跑」、归属需求交付、自动合并）都到 `done-none`，写「没有运行合并后的流程，没有什么要再等的」。有一项没成功时 `run-workflows` 让这一步失败、整个运行失败，错误里写明是哪一项，不另加错误边界。

### 放弃后的流程

监督开发另声明挂点 `abandoned`：「需求进行中」选「放弃」、暂停后选「放弃」两条路径结束前都先调用它，项目用 `<coda:join hook="abandoned" …/>` 加入，在这里收回这个需求占着的东西（如它的泳道实例）。用 `run-workflows`（`hook=abandoned`，`inputs` 是 `run`（本次需求运行的 ID）和 `branch`（需求分支））运行：不出卡，加入者全跑，不传 `only` 与 `commit`（放弃时没有合并提交，用本次运行的提交）；一个没成功运行就失败，没有加入者时直接结束。外部取消运行不触发，需求交付的放弃也不触发。composer 只传 `run` 和 `branch`，不认识项目的目录和流程名。

### 提交验收时跟上目标分支

「提交验收」之后、开 PR 之前，「跟上目标分支」（`sync-base`）在步骤工作区 fetch 目标分支（`base`，留空为仓库默认分支）和需求分支，固定两端提交，按情形处理：

| 情形 | 做法 |
| --- | --- |
| 需求分支已包含目标分支 | 不动 |
| 需求分支是目标分支的祖先 | 把需求分支快进到目标分支 |
| 分叉、能干净合并（`git merge-tree` 试合并） | 在步骤工作区做一个保留双亲的合并提交（需求分支在前、目标分支在后），推到需求分支 |
| 有冲突，填了开工执行者 `executor` | 「执行者合并目标分支」（`sync-resolve`）：从固定的需求分支 head 新开执行会话，把固定的目标分支提交合并（merge，不变基）进来、解冲突、顺延撞号的迁移版本、提交合并提交；它的 head 同时包含两端时由流程推到需求分支，否则带着它的回答回到「需求进行中」。执行会话失败但给出了会话 ID 时记进 `develop.json` 的 `sync.session`，这一步再跑用 `--continue` 接回它、先核对现场（接不回、回复里没有会话 ID 才从需求分支 head 新开一次）；拿到会话先落盘再推需求分支，推送因网络失败退出时再跑也接回同一会话，推成功后清掉 |
| 有冲突，没填开工执行者 | 带着冲突的文件回到「需求进行中」，主 Agent 选「跟上目标分支」派一块（备注最前面写执行者） |

推到需求分支都是普通推送（不 force）。被拒且需求分支已经不是固定的那个提交（被别的提交推进了）时不重试、不覆盖，带着原因回到「需求进行中」；需求分支没动的推送失败保留原退出码。
之后新 head 照常开 PR、跑全部检查（项目检查、合并前检查、GitHub 检查），不跳过；合并提交和执行者解冲突的提交列进汇总的「流程直接推到需求分支的提交」。最后合并时目标分支又变了、冲突了，仍按上文第 9 步回到「需求进行中」。

### 整体评审

项目检查有了结论（同一 head 复用的，或刚跑通过的）之后，「定整体评审」（`overall-plan`）决定这次评不评，三样都满足才评：

- 填了 `overallReviewer`；
- 不是只合进了一块且它评成过：合进的块是目标分支最新提交到需求分支 head 之间说明带 `Coda-Piece:` 的提交（开 PR 时把它们的运行 ID 记进 `develop.json` 的 `landed`），跟上目标分支的块（执行者的合并提交）和流程直接推的提交不带它，不算；块合入时输出 `reviewed`（最后一次交付有没有评成的评审），评成的记进 `reviewedPieces`。只合进了一块、它的最后一次交付评成过的，块的评审已经看过同一份改动，跳过；这一块没评审者（开工没填 `reviewer`、派块写了「评审者：无」）或没评成的照常评；
- 这次运行还没评过：评完一次（`review-commit` 给出了结论，没评成不算）之后再「提交验收」不再评；这次提交勾了「重新整体评审」就当没评过，照常评一次。

评的时候用 `callActivity calledElement="review-commit"` 按名字调一次评审能力：`reviewer` 是 `overallReviewer`，`base` 是目标分支的最新提交、`head` 是需求分支 head（评的是两者的三点 diff，即整条需求分支），`task` 是需求名、目标与完成标准和主 Agent 的汇报，`evidence` 是项目检查的结果。不带 `previous`，不增量复评。
评审没完成时 `review-commit` 照常结束（`decision` 为 `INCOMPLETE`），记为没评成；调用本身没成时出错边界接住（「记下整体评审没评成」），同样记为没评成。都不重试、不换人。评完的结果按级别（`level`）分开记进 `develop.json` 的 `overall`，评审原文写在 `$CODA_ARTIFACTS/overall-review-<第几次>.md`；出过必须修就记下 `overallMust`，这次运行之后都不自动合并。

评不评都经过「整理整体评审」（`overall`）：

| 情形 | 去向 |
| --- | --- |
| 这次没评，或评了没有必须修 | 往下走（设备验收、合并前检查……）；最近一次评完的小问题（标题、位置、说明）和原有问题写进 PR 描述，批准卡和待交付卡的汇总也带上，不是在当前 head 上评的写明评审时的 head |
| 这次评了，有必须修或没评成 | 主 Agent 的「整体评审结论」 |

它还输出自动合并的判定 `auto`（开了 `autoMerge`；这次运行评成过：整体评审评完过，或合进的每一块最后一次交付都评成过；且 `overallMust` 没记下。一次都没评成过的照常出批准卡），以及批准卡上「整条需求分支已整体评审」那半句（评过才有，不是当前 head 时写评审时的 head）。

「整体评审结论」是一页结论：需求、PR、需求分支 head，评审者的一句话结论，必须修几条、每条一句加位置，小问题、原有问题只给条数，评审原文的路径；没评成时写原因（调用没成的指向本运行的「评审整条需求分支」）。卡上的取舍标准同「需求进行中」。主 Agent 选「继续验收」往下走；选「回到进行中」时备注可选，连同这一页结论带回「需求进行中」，派块修好后再提交验收，这时已经评过，不再评，要再评就勾「重新整体评审」。

需要 review 插件 4.0.0 及以上（发现的级别 `level`：`must`、`nit`、`existing`）。

### 改动区域

PR 汇总的改动块统计目标分支最新提交与需求分支 head 的三点 diff（与 GitHub PR 的 Files changed 一致），按区域列出文件数和增删行数，区域按增删总行数从多到少排。改名按新路径归类，二进制文件计入文件数、行数记 0。

区域由需求分支 head 上的 `.coda/areas.json` 声明，格式为 `{ "区域名": ["路径前缀", ...] }`，前缀是普通字符串前缀，如 `iOS/`、`Sources/CodaCore/`、`AGENTS.md`。一个文件归入最长匹配前缀所在的区域；都不匹配时归到它的顶层目录名，根目录下的文件归「根目录」。没有这个文件时全部按顶层目录归类；文件存在但 JSON 写坏时开 PR 步骤直接失败。

### 设备占用

填写 `device` 且开启设备验收时，安装前先调用 testbed 的 `resolve-testbed` 按设备名解析，再用 `hold-group` 占用返回的组（容量 1），状态显示「等验收设备 <设备名>」。引擎按组归属在整个空间排队；composer 不新增 testbed 硬依赖；填写设备名使用验收时须安装 testbed。安装与验收共用这一段占用，发起 `ios-preview-install` 时除精确 `commit` 外还传同一个 `device`，安装运行借用本段设备，不另排队。通过、回到进行中或取消并收尾后释放；再次进入重新排队。缺少必填意见时仍留在本段补填。未填设备名时不传设备参数、不占设备。

填写 `hold` 时，正常进入本段时先后占两把锁：先用 `hold-group` 占这个组（容量 1），状态显示「等 <组名>」，再占验收设备；先组、后设备，顺序固定。两把锁都写 `borrow="no"`：本段自己的申请独立排队，不向别人借；本段发起的运行（安装卡、验收卡里发起的）可以向本段借。和设备一样，离开本段就放开，再次进入重新排队；留空不占。它给项目里同一时间只能给一个需求用的东西，如只有一台的需求分支专用后端：项目的部署流程整条运行占着同一个组，主 Agent 在安装卡上发起的部署借用本段的组直接进，别的要用这个组的运行（如别的需求合并后的部署）按这个组的名额排队。组名和要发起哪个流程由项目自己说明，composer 只照传的组名占。

使用约定（composer 不加机制强制）：

- `hold` 只填一个环境组，比如项目给需求分支专用的后端部署组；不要填别的设备的组，设备用 `device` 填；也不要填 `host` 这类构建名额组。填错了可能卡住。
- `hold` 正好填成本设备的组（`device` 解析出的那个组）时，本段已经占着它，不会再占第二次。两条需求交叉把对方设备的组填进 `hold`，会互相等住，属于填错，不处理。
- 代价：填了 `hold` 又要等设备时，等设备的整段时间里，`hold` 的环境组一直被本段占着，别的要用这个组的运行也得等。
- 安装要用的、会和别的需求共用的环境组，要填进 `hold`。先组后设备的顺序保证以此为前提，composer 没法强制。
- `borrow="no"` 只保证本段自己的申请独立排队。宿主按会话认出借方，同一会话发起的其他运行仍可能借到。
- 原地恢复时，宿主会把这一段占过的锁一次全部重排，罕见情况下仍可能互相等住，这次不处理。
- 需求交付（`deliver`）没有 `hold`。它的安装要用别的需求作为 `hold` 占着的共用组时，仍可能互相等住。

### 不触发 PR 生命流程

流程步骤替运行所属的会话说话（`CODA_THREAD_ID`），GitHub 插件的 `gh` 会把它 `gh pr create` 开的 PR 报给「PR 观察」，PR 观察再发布 `pull_request.opened` 等事件，review 插件的 PR 生命流程（`pull-request`）就会自动跟上同一个 PR：
它会再跑一遍检查、评审，进目标分支的 PR 还会再出一张批准卡。所以监督开发开 PR 时去掉 `CODA_THREAD_ID`（`scripts/shared.mjs` 的 `openPr`），这个 PR 不上报，PR 观察和 PR 生命流程都不会因它启动；检查、评审、合并都由开它的流程自己做。
代价是这个 PR 不在会话的「报过的 PR」里（GitHub 插件的 `github-reported-pr` 找不到它），要手动评审时直接传 PR 地址。

## 块

「块」（`piece`）是需求运行里的一项改动：主 Agent 在「需求进行中」选「派一块」或「跟上目标分支」，需求运行用 `callActivity` 调起它（下文「派块」），执行者写代码，经项目检查、评审和主 Agent 的审查后合进需求分支，结果交回需求运行。
写的人自验，机器检查，一位评审者评，主 Agent 看一页结论取舍；主 Agent 只拆块和取舍，不读 diff。
它不开 GitHub PR：一个需求在 GitHub 上只有需求分支进目标分支的那一个 PR。它不装机、不部署、不跑合并前检查（这些只在需求分支进目标分支时做一次）；只有同一块退回满三次、主 Agent 还要退回时才出你的卡（下文「退回与复评」）。一项就是一块，一次只派一块，结束后才派下一块。
块需要的都由输入给出，不按需求运行 ID 去查。

| 输入 | 用途 |
| --- | --- |
| `branch` | 必填，需求分支名；执行者从它的 head 开工，这一块合进它 |
| `base` | 必填，目标分支（需求最后合进的分支）；`sync=true` 的块把 `origin/<base>` 合并进来 |
| `title` | 必填，块的名字，用在运行标题里；普通块合入时是 squash 提交的标题，跟上目标分支的块合入的是执行者自己的合并提交，不用它 |
| `task` | 必填，自足的任务书：背景、范围与验收要求 |
| `sync` | 布尔值「跟上目标分支」，默认关；见下文「跟上目标分支」 |
| `executor` | 必填「执行者」，一组 Agent 选择（Agent、模型、强度、模式与其他选项，流程参数的 `agent` 类型），通常是所属监督开发的开工执行者；没有默认值，不传时启动就报「需要参数 executor」，不再落到发起会话。没选的模型、强度、模式用执行者的默认值，其他选项逐个传给 `coda-agent --option` |
| `executor2` | 「备用执行者」，没有默认值，不填就是空（`null`）；见下文「备用执行者与退回次数」 |
| `reviewer` | 「评审者」，没有默认值，不填就不评；填了就评每一次交付，见下文「评审」 |

1. **执行**：用 `coda-agent --commit <需求分支当前 head> --json` 开执行会话。固定说明要求遵守 AGENTS.md，只做本项、在当前分支提交、不推送、不写防御性或冗余代码、不顺手重构；只跑与改动直接相关的快检查，流程会在审查前自己跑项目检查，构建、全套和界面检查不重复跑，不必再用 run-held 跑整套编译；只跑改动直接涉及的测试文件，不跑无文件参数的 `check.sh backend`、`--all`、完整 workflows 套件、客户端编译（任务明确要求的除外）；验证命令要把原始检查的退出码传出去（直接执行检查命令，要看日志尾部就用 `rc=0; <检查> > "$log" 2>&1 || rc=$?; tail -n 80 "$log"; exit "$rc"`：run-held 在 zsh 里执行，`status` 是 zsh 的只读变量，不能用作变量名；不能只 echo 退出码，不能让最后的 tail / grep / cmp 决定成败）；改坏验证只跑命中的那个用例、沿用默认时限，挂住了先定位原因；run-held 和流程运行的结果会自己送回，不另起 Monitor 或后台任务盯日志；并报告实际验证。
   固定说明还规定交块的格式：回答的最后一条消息以单独一行「交付说明」开头，其下固定给两段——任务书的完成标准逐条做到没有（没做到写原因）；怎么把改动跑起来验的（命令或操作与结果，没跑就写「没跑」和原因）。`coda-agent` 的 `answer` 是这一次说过的全部话（含中途的进度），审查卡的「执行者最后一条回复」从最后一行「交付说明」起取；执行者没按格式写时放这一次的全部回答，开头注明没按格式。
   执行者的分支/head 必须在本机仓库可读；`coda-agent --json` 标准输出是一行 `{session, branch, head, answer}`，`--continue` 保留同一会话并遵守首次的退出码约定。
   执行步骤失败后恢复（`workflow_resume`）或重试再跑时接回这一步已开的会话：会话失败、取消或结果未知时 `coda-agent` 仍在标准输出给出会话 ID，流程在 `$CODA_ARTIFACTS/piece.json` 的 `opening` 里完整记下待完成的动作：`action`（`execute`、`swap` 或 `revise`）、`text`（任务文字）、`agent`（这个动作该用的执行者配置：`execute` 用当前执行者（首次执行还没有 `executor` 时用 `executor` 参数），`swap` 用备用执行者，`revise` 用当前执行者）、`session`（有会话才有）。动作开始前就写入，拿到会话 ID 后补上；只有动作成功才清掉并把会话写进 `executor`，中途怎么失败都不清。再跑时有 `session` 就用 `--continue` 发一段续跑说明——先核对现场（`git status`、`git log`、上次做到哪），再接着完成原任务，不要从头重做——后面附任务书；没有就用 `opening.agent` 从需求分支 head 新开。步骤被杀或后端重启而没拿到标准输出时记不下会话 ID，只能新开。运行从头重跑（插件更新后恢复时流程定义变了，会从开始事件重走）时 `execute` 以上一次的完整状态为底（状态文件已在），只重写自己的输入（需求分支、目标分支、临时分支、标题、任务、是否跟上目标分支），其余原样保留（`opening`、`executor`、当前执行者配置、检查失败计数、退回次数等），首次开工才新建：有 `opening` 就做它描述的那个动作（不管是 `execute`、`swap` 还是 `revise`），换人的决定和备用会话已做的提交不会被吞掉；没有 `opening` 才用 `--continue` 接回 `executor.session`，同样先发续跑说明，不再从需求分支 head 另开会话、推翻已审查的提交；换过备用执行者后当前执行者（状态里的 `agent`）就是备用的，接不回时回退新开用的也是它，不因从头重跑退回流程参数里的原执行者；连续检查失败计数只在这次成功的会话是新开的（`--commit`）时清零，接回已有会话（退回修改、从头重跑、恢复）的不清；`swap` 没有 `opening` 时是有意新开，不在此列。「退回修改」本来接回同一会话，它失败后再跑（`opening` 记 `revise`）也先发续跑说明。`--continue` 接回的会话接不回时，Coda 侧的流程 Agent 步骤已在同一会话里续跑可恢复的失败，所以 `coda-agent` 失败就是终局，再按回复里有没有会话 ID 分两种：回复里没有 `session`（不管退出码；输出不是 JSON 也算）才算会话接不回，输出写明原因，只去掉 `opening.session`，同一次里用 `opening.agent` 和 `--commit <需求分支当前 head>` 新开会话、给原任务，新会话写回 `opening.session`，只回退一次；新开也失败时 `opening` 照样留着，下次重跑仍是同一个动作。回复里有 `session` 但失败（非零退出，或缺 `branch`、`head`）不新开：会话和它做出的提交还在，保留 `opening.session`（回复里的会话和记下的不同就改记回复里的），按失败退出，下次恢复继续 `--continue` 同一会话，不会被新会话的强推替换。退回修改接不回不新开：新开的会话没有已交付的提交和审查意见，修改必须在原会话里做，按失败处理并在输出里说明，记录留着。
2. **推送到临时分支**：把执行者的 head 强推到本运行的临时分支 `piece/<运行 ID>`，项目检查和评审从远端取得到这次交付；之后的交付推同一个分支。不开 PR。推送失败停在这一步，日志保留 Git 的具体原因；网络类失败（DNS、超时、连接重置、TLS、服务端 5xx）由 Coda 按 `coda:retry="3"` 自动再跑，同一个提交推同一个分支，重跑是幂等的。
3. **项目检查**：普通的块（`sync=false`）交付相对需求分支没有新提交时不进检查和评审，同检查没过一样自动交回同一执行会话，说明写「这次交付相对需求分支 <分支名> 没有新提交：先 git status 看工作区，把这一项的改动提交到当前分支再回报」，计入连续失败次数；跟上目标分支的块（`sync=true`）没有新提交是正常的（目标分支已包含在内），不拦。有新提交时在这个 head 上跑项目加入挂点 `check` 的流程。失败时前两次自动交回同一执行会话，写明提交和本运行链接，由执行者用 `workflow_status` 读失败流程、步骤和日志；第三次连同三次记录交给主 Agent 审查，不评审。通过会清零连续失败次数。
4. **评审**：填了评审者就调一次 `review-commit`，见下文「评审」。评审的结论不决定去向：评完（含没评成）就整理材料、出主 Agent 的审查卡。
5. **主 Agent 审查**：一页结论，见下文「审查卡」。答复有五种：
   - 「退回修改」：备注必填，同一个执行会话（`--continue`）按它修，之后照常检查、复评（下文「退回与复评」）；满三次后再选它不退回，交你决定。
   - 「让执行者合并需求分支」：备注可选；同一个执行会话把需求分支当前 head 合进来（见下文「合并需求分支」），不算退回。
   - 「换备用执行者重做」：备注必填；见下文「备用执行者与退回次数」。
   - 「合进需求分支」：见下文「合进需求分支」。
   - 「放弃」：删掉临时分支（已不在就跳过），需求分支不动，运行走到出错结束「主 Agent 放弃了这一块，需求分支没动」。

   必填备注没写时回到审查卡，「待处理反馈」里写明缺什么。修改都交给执行者，主 Agent 不自己改代码。

由需求运行调用时结果交给需求运行，不另送回会话。合进需求分支时正常结束，输出 `commit`：合进需求分支的提交（普通的块是 squash 得到的那个提交，跟上目标分支的块是执行者的合并提交），以及 `run`：本运行 ID，需求运行把两样写进下一次「需求进行中」；还有 `reviewed`：这一块最后一次交付有没有评成的评审（`true` / `false`），需求运行据此定整体评审与自动合并（上文「整体评审」）。
没合入就以失败结束，调用方拿得到原因：主 Agent 放弃时走出错结束，运行以「流程走到出错结束「主 Agent 放弃了这一块，需求分支没动」」失败；步骤失败没接住时以那一步的失败原因结束。用 `callActivity calledElement="piece"` 调它的流程在出错边界上接住（`CALL_FAILED`，原因随错误带上）。
执行会话、反馈与评审账本暂存于 `$CODA_ARTIFACTS/piece.json`。

### 合进需求分支

主 Agent 选「合进需求分支」后，流程先 fetch 需求分支当前 head（别的块可能刚合进去），先认这一块是否已经合入，重跑这一步不会合入两次：
普通的块在需求分支里找说明带 `Coda-Piece: <运行 ID>` 的提交，找到就原样交出它；跟上目标分支的块看推送前记在 `piece.json` 的 `landing`（运行从头重跑 `execute` 会换掉执行者的 head，这条记录还在）或这次交付是不是已是需求分支的祖先，是就原样交出。都没有才合：

- 普通的块用 `git merge-tree --write-tree` 试合并需求分支 head 与这次交付。只是试：不产生提交，不动任何引用、索引和工作区（只会在对象库里留下几个可回收的临时对象）；冲突时能按文件名列出。
  有冲突就不动需求分支，把下文的固定说明连同冲突的文件交给同一个执行会话合并（只合并，不变基），之后照常推送、检查、评审，再回到审查卡，不算退回。
  干净时把试合并得到的树做成一个提交（`git commit-tree`），父提交是需求分支 head，说明是 `title`、空一行、`Coda-Piece: <运行 ID>`：这一块不管执行者交了几个提交都是一个提交。再普通推送到需求分支，只快进、不强推；推送被拒（需求分支在这期间又动了）这一步失败，恢复时重新 fetch、重新试合并。
- 跟上目标分支的块（`sync=true`）不 squash：需求分支 head 是这次交付的祖先时，把需求分支快进到执行者的合并提交（不强推）；不是祖先时同样交回执行者先合并需求分支（能干净合并时不列冲突文件）。

合入后删掉临时分支（已不在就跳过）。

### 合并需求分支

「让执行者合并需求分支」和试合并发现冲突给执行者的是同一段固定说明：需求分支是哪一条、别的块可能已经合进去了，试合并时列出冲突的文件；要求先 `git fetch origin <需求分支>`，把它合并（不是变基）进当前分支——变基会改写已经审查过的提交；解决冲突，数据库迁移等版本号和需求分支撞号时顺延自己这边的；跑和冲突相关的测试后提交，只做这件事，回报冲突了哪些文件、各自怎么解决的、跑了什么；需求分支没有新提交时直接回报不需要合并。主 Agent 写了备注就附在后面。两种都不加退回次数。

### 跟上目标分支

需求分支活得久，目标分支动得快。主 Agent 在「需求进行中」选「跟上目标分支」，需求运行派一个 `sync=true` 的块，标题是「跟上 <目标分支>」，任务固定是把目标分支最新的提交合进需求分支、解冲突、顺延撞号的迁移版本（主 Agent 的备注附在后面）。块的流程在任务书后再附上固定说明：先 `git fetch origin <base>`，把 `origin/<base>` 合并（merge）进当前分支，不要变基、不要压成一个提交；它以合并提交快进进需求分支，保住需求分支与目标分支的祖先关系；迁移版本号撞号时顺延需求分支这边的。
合进需求分支时用快进而不是 squash：squash 会丢掉与目标分支的祖先关系，之后需求分支进目标分支时同样的冲突会再来一遍。

### 评审

评审在项目检查通过之后、「整理审查材料」之前；检查没过不评，连续三次检查失败直接交主 Agent 审查的那条路也不经过它。没填 `reviewer` 时不评。
「记录检查并定评审范围」（`gate-passed`）记下检查结果，定这次怎么评，再用 `callActivity calledElement="review-commit"` 按名字调一次评审能力：

- `head` 是这次推送的提交，`reviewer` 是评审者，`evidence`（已有验证）是这次交付的项目检查结果，和审查卡上「项目检查结果」是同一段文字；
- 第一次评审，以及换备用执行者、合并需求分支（主 Agent 选的和试合并冲突交回的都算）之后：`base` 是推送时记下的需求分支 head（评的是三点 diff，别的块合进需求分支不混进来），`previous` 为空；之前没关的必须修作废（`superseded`），由这次的结果代替。换人或合并时清掉「上次评成的提交」，所以这次完整评审没评成、主 Agent 又退回时仍是完整评审，到有一次完整评审评成为止都是；
- 主 Agent「退回修改」之后是复评：`base` 是上次评过的提交，只评之后的变动；`previous` 带上还没关的必须修（编号、级别、类别、标题、位置、说明），评审者对每条给出 `resolved`、`upheld` 或 `withdrawn`。中间检查失败的自动续作不改变这一点；
- `task` 是任务书原文，主 Agent 退回过就在后面附上历次的退回意见原文（按先后），只作参考，并说明其中写明不改的已经关闭、不要再提；意见里评审者只看得到编号，所以定了不改（`declined`）的每条另列编号、标题和位置，让它不把这些当新问题再提。

评审之后「评审结果入账」（`reviewed`）：只有必须修（`level` 为 `must`）记进账本（`piece.json` 的 `findings`），编号 `#1`、`#2`……接着编、之后几轮沿用；复评的结论改旧条目的状态，坚持的（`upheld`）仍开着；评审原文写在 `$CODA_ARTIFACTS/review-<第几次>.md`。
复评坚持（`upheld`）的条目记下评审者给的 `reason`，审查卡上跟在那条后面（「现在的代码还缺：…」）。
评审没完成（`decision` 为 `INCOMPLETE`）不入账，下一次复评仍从上次评过的提交算起（换人或合并之后的完整评审没评成，则仍是完整评审）；复评没评成（没完成或调用没成）时审查卡仍列出上一轮还开着的必须修，注明「这一轮没有重新核实」；调用本身没成（没有插件提供 `review-commit`、参数不合法、评审步骤到了时限）由出错边界接住，记为没评成。两种都不重试、不换人，照常出审查卡。

需要 review 插件 4.0.0 及以上（发现的级别 `level`：`must`、`nit`、`existing`），以及 0.3.32 及以上的 Coda（Coda #2435：没填的评审者、备用执行者是空的 Agent 参数，按名字调用时要算作没传）。

### 审查卡

「整理审查材料」（`report`）把这一块整理成一页结论，主 Agent 不必读 diff。卡上依次是：

1. 执行会话、head 与临时分支、需求分支、已退回次数、备用执行者；
2. 执行者最后一条回复（上文第 1 步的两段）；
3. 项目检查结果：每个检查一行（流程名、结果、运行链接），项目没有声明检查流程时是那一句说明；检查没过时写「此提交项目检查未通过。」；
4. 评审结论：评审者的一句话结论；必须修几条，每条一句加位置（评审者认为涉及对外契约或任务范围的标出来）；小问题、原有问题只给条数，其中涉及对外契约或任务范围的列标题；评审原文的路径。没填评审者、检查没过、没评成时各写一句；
5. 改动范围：推送时记下的需求分支 head 到这次交付的三点 diff，与评审看的是同一份；文件数、增删行数和按区域的统计，算法与监督开发的「改动区域」是同一份（`shared.mjs` 的 `changes`）；
6. 看改动的命令，留一行备查：`git fetch origin <需求分支> <临时分支> && git diff <需求分支 head>...<head>`；
7. 待处理反馈（有才写）：检查连续失败的记录、备注没写回到卡上的原因等。

卡上的说明：

- 不要求读 diff。只在三种情况下读有疑问的那部分：评审者说动了对外契约或超出任务书；执行者和评审者各执一词；改动范围明显超出任务书。
- 取舍标准（和「需求进行中」「整体评审结论」同一套说法）：只有必须修才退回，评审者说成立不等于现在要修；必须修是合并后用户会遇到错的结果、丢数据、安全问题，对外契约写错，测试是红的或会偶发失败，漏了任务书要求的事或做了任务书之外的事，以及会扩散、越晚越难改的结构问题（跨模块或会被照着写：绕过已有边界、依赖方向反过来、第二个事实来源或第二套做同一件事的机制、迁移只做一半），其余是小问题。退回时只列要修的那几条，定了不改的单独一行写「#编号 不改」，后面可以接理由，如「#2 不改：只影响少见路径」；不顺手带小问题，不加设计改动，不把以后的需求提前做进来。
- 其余答复（让执行者合并需求分支、换备用执行者重做、合进需求分支、放弃）的说明见上文第 5 步。

### 退回与复评

「退回修改」后执行者在同一会话按备注修，照常推送、过项目检查，再由评审者复评（上文「评审」）。备注里单独一行写 `#编号 不改`、后面可以接理由的那条（如 `- #2 不改：只影响少见路径`：行首只允许空白或列表符号 `-`、`*`，「不改」后面是行尾，或「：」「:」「，」「,」接理由；「修 #1，#1 不改会继续导致失败」「#3 不改的话会失败」这类句子里提到的不算）由流程就此关掉（`declined`）：之后复评的 `previous` 不带它，评审者不再给它结论，不依赖评审者照办。

同一块「退回修改」满三次后，主 Agent 再选退回时不退回，出一张给你的卡「这一块三轮没过」（`stuck`），列出主 Agent 这次的退回意见和还开着的必须修，两个选择：

- 「继续修」：退回次数清零，按主 Agent 这次的意见退回（这次算新一轮的第一次）；
- 「放弃这一块」：同主 Agent 选放弃。

### 备用执行者与退回次数

- 「换备用执行者重做」的备注写为什么换、接手的人要注意什么。流程用 `executor2` 从需求分支当前 head 新开一个执行会话，重做同一项：上一位没被接受的提交不带过来；这一步自己失败后再跑时接回这次新开的备用执行者会话，不再另开；给它的是固定的执行者说明、这一项的任务书原文、这次的备注，再加一句上一位执行者的分支与提交在哪里、可以参考也可以不用。
- 之后照常推送、检查、评审（完整评审）、审查。新会话连续检查失败的计数重新开始；再「退回修改」续的是新会话。主 Agent 可以再换一次，同样新开一个备用执行者的会话。换不换只由主 Agent 决定，流程不按退回次数自己换。
- 没填 `executor2` 时不能换。Coda 的流程方言只能按条件隐藏勾选项（`coda:option` 的 `coda:shown`），不能隐藏答复本身，所以这个答复总在卡上：卡上写着「备用执行者：未指定，不能换人」；选了就回到审查卡，「待处理反馈」里写明没有填备用执行者，运行不失败。

审查卡写「已退回 N 次」，0 次也写。只有主 Agent 选「退回修改」（备注写了）才加一；项目检查失败的自动续作、换备用执行者、合并需求分支（两种都是）、备注没写回到卡上都不算；同一项换人不归零，只有你在「这一块三轮没过」选「继续修」时清零。

## 需求交付流程

一个需求跨几个仓库、要一起验收、一起批准时才用它；单仓库的需求直接用监督开发。在**交付并部署这个需求的项目**的会话里开启「需求交付」（`deliver`）：`title`（需求名）默认空，目标与完成标准是发起时带的需求文字（`run.message`），`devices`（是否设备验收）默认关，可选 `device`（验收设备名，如 `duo-testbed`，默认空），与监督开发一样：都会解析设备，并在验收期间一直占着。差别是监督开发的 `device-lock` 带 `borrow="no"`，独立排队；需求交付没有，同一会话已占着这台设备时，需求交付可能借到它。

0. 需求名和需求文字缺一样时（如你开启的），先交主 Agent「写需求」，同样不叫醒它、随下一条消息告诉它。主 Agent 答复时备注必填：第一行需求名，空一行后是目标与完成标准。任务里写明之后怎么做：为每个要改的仓库在那里用 `workflow_run` 发起 `develop`（成员需求运行），传 `title`、`message`（这个仓库要做的部分与完成标准）、`delivery=<本运行 ID>`、`devices=false`，以及为这个成员选的执行者、备用执行者、评审者和整体评审者（`executor`、`executor2`、`reviewer`、`overallReviewer`），跨仓库用 `project`；主 Agent 在各成员的「需求进行中」选「派一块」把改动一块块合进它的需求分支，做完提交验收，检查通过后停在「待交付」。

1. 主 Agent 在「确认达标」选择「开始交付」，备注每行一个成员 PR URL（各需求分支进目标分支的 PR），按合并顺序排列，被依赖的仓库在前。流程记录各 PR 的 URL、head、分支及 base；选择「放弃」结束。
2. 开启设备验收时，以最新 `origin/<base>` 创建 `delivery/<运行 ID>`（分支名只用 ASCII），按顺序 `git merge --no-ff` 仅合入本仓库成员的已记录 head 并推送。集成失败经错误边界回到确认，合并冲突的具体 Git 输出作为反馈。新一轮从最新 base 重新集成并替换本运行的预览分支。
3. 主 Agent 用集成提交只安装改到的那一端（`mac-preview-install`、`ios-preview-install`），发起的安装都成功后答「已装好」；「回到确认」须附原因。用户统一设备验收一次，「不行」须附意见并回到确认。主 Agent 在相关成员的「待交付」选「退回修改」，它回到「需求进行中」，派一块修好、重新提交验收并检查通过后再集成、安装、验收。`devices=false` 跳过集成、安装及设备验收。
4. 主 Agent 写约 15 行以内的交付汇报，备注作为批准卡正文：交付名、用户能感知的 3～5 条变化、结构变化（无则写「无」）、设备与检查结论、部署后真实环境验证计划、风险与未做事项（没有可省略）、PR 链接。不放执行者原文、测试数量、文件清单或代码。
5. 用户「批准交付」卡只显示汇报和全部成员 PR；「批准合并」的勾选项是本项目（本仓库最后一个成员的 head）上加入挂点 `merged` 的流程（见监督开发「合并后的流程」）。「暂不合并」必须附言（原因）并返回确认；设备验收的「不行」同样必须附言，可以只附截图，路径随反馈交回主 Agent。批准后进入「放行合并」。由任务叫醒发起会话，不再单独通知选择。
6. 主 Agent 按顺序放行成员，被依赖的仓库在前：先放行提供被钉版本的包的成员的「待交付」，等合并并发布新版本；再退回钉这些包的仓库成员，回到它的「需求进行中」派一块更新钉定的包版本，重新提交验收、检查通过后回到待交付；最后放行依赖方成员。成员都以合并提交合并。全部合并后备注写本项目最后一个合并提交，没有本仓库成员时写本项目当前目标分支提交。
7. 在该合并提交上运行勾了的合并后流程（卡上没写的文字先交主 Agent 补写，同监督开发「合并后的流程」）。随后主 Agent 按目标走真实环境验证，选「通过」或附具体意见选「有问题」，用 `tell-session` 告知发起会话后结束。一个都没勾，或勾了的都选了「这一项这次不跑」时，仍验证当前真实环境，备注说明没有部署造成的未验证部分；验证说明与告诉发起会话的结论里说的合并后流程，按实际运行的（跳过之后的 `only`）算，不按批准时勾的。

必填备注缺少时回原任务补填。成员快照、轮次和反馈保存在 `$CODA_ARTIFACTS/deliver.json`；运行之间只通过主 Agent 答复各自人工任务协调，不直接发消息。此流程不改变成员需求运行的检查与合并路径。
