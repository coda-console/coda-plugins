# 输入框模式

`@coda-console/composer` 把输入框的五种模式放在同一个插件里，插件 ID 为 `composer`；另带两个开发流程：监督开发（`develop`，一个需求一条需求分支）与需求交付（`deliver`），以及监督开发里主 Agent 往需求分支提改动用的「块」（`piece`）。开发流程由你在输入框「＋」里开启，或由 Agent 用 `workflow_run` 带 `confirm: true` 填好、你在开工卡上确认（Coda 的开工卡）。

| 模式 | 入口 | 用途 |
| --- | --- | --- |
| 交接到新会话 | `/handoff` | 新会话承接当前上下文，共享工作目录；原会话保留，可继续使用。 |
| 子会话 | `/subagent` | 从任意会话启动子会话，承接近期上下文并沿用工作目录；可选完成后回报父会话或你。 |
| 执行命令 | `!` | 在会话工作目录执行命令，命令与结果作为消息发给 Agent；也可在新任务输入框使用。 |
| Ultra | `/ultra` | 主 Agent 定任务、做决定、审查，不改代码的调研与核实按任务交给名单里的执行者；也可在新任务输入框使用。 |
| 循环 | `/loop` | 按周期把同一句话再发给 Agent，每轮做完才开始计时，7 天后自动结束；仅用于已有会话。 |

五个模式可同时开启，模式 ID 不变。Ultra 开启时，从这个输入框创建的新会话（包括子会话、交接和新任务）继承 Ultra 及当前子 Agent 名单，各自独立保留模式；关闭来源的 Ultra 不会关闭已创建会话的 Ultra。工具栏始终选择输入框自己的执行者；交接与子会话的参数另有可选 Agent，留空沿用输入框执行者。子会话也能创建自己的子会话。

10.0.0 监督开发（`develop`）加输入 `executor`、`executor2`：开工时就能看到、能改本泳道的默认执行者与备用执行者，「需求进行中」任务里把它们写成可原样传给 `workflow_run` 的 JSON；需求交付为各成员开工时也为每个成员选执行者。泳道 PR（`lane-pr`）的 `executor` 由可省略改为必填，不再默认取发起会话的 Agent（原来漏填时悄悄落到最贵的主会话模型），不传的旧调用启动时即报「需要参数 executor」，与旧版不兼容；主 Agent 仍可按块另定。Ultra 名单的范围加上 `develop` 的 `executor`、`executor2`。

10.1.0 让瞬时故障原地恢复（[Coda #2642](https://github.com/coda-console/coda/issues/2642)）：只做幂等网络操作的脚本步骤声明 `coda:retry="3"`（泳道 PR 的推送并开 PR、合进泳道、关闭 PR，监督开发的建泳道、开 PR 或更新汇总、GitHub 检查、合并，需求交付的记录成员 PR），网络类失败时由 Coda 自动再跑，不再靠主 Agent 手动恢复；泳道 PR 的执行、换备用执行者失败后再跑时接回这一步已开的执行会话，不再另开新会话重做。需要支持 `coda:retry` 的 Coda（协议 6.0.0）。

10.2.0 泳道 PR 的评审意见先在执行者和评审者之间收敛，收敛了或收敛不了再交主 Agent 审查（下文「评审收敛」）；执行者固定说明加上只跑涉及的测试文件、验证命令传出原始退出码、改坏验证只跑命中的用例、不另起 Monitor 盯日志。原有步骤的动作与输入输出不变，新行为都是新动作、新节点，已在跑的运行按开工时的定义照旧走。需要 review 插件 3.4.0 及以上（`review-commit` 的 `previous` 输入与 `resolutions`、`blocking` 输出）。

10.3.0 Ultra 去掉每轮短提醒：一轮结束时只有首次、改名单要给完整说明时才 `tell`，否则什么都不发；压缩由 `coda/composer@1` 的 `status.compactions` 识别，变大就立即给完整说明（原来按 Ultra 的 `sent` 由大于 0 变 0 推断，两次压缩之间没有用户消息就漏掉）。名单措辞改成通用一句，不再点名 `lane-pr`、`develop` 的输入；监督开发（`develop`）任务里 `reviewer`、`reviewer2` 的选法补上「有执行者名单就从名单选」。需要在压缩完成时给输入框 `status.compactions` 加 1 的 Coda，不兼容旧版。

11.0.0 按 [Coda #2788](https://github.com/coda-console/coda/issues/2788) 把「泳道 PR」（`lane-pr`）改名为「块」（`piece`），不留兼容或别名：泳道只指一个需求的运行环境，代码所在的分支叫需求分支，监督开发里执行者做的一段叫块。块不再开 GitHub PR，一个需求在 GitHub 上只有进目标分支的那一个 PR：交付推到临时分支 `piece/<运行 ID>` 供项目检查和评审（`review-commit` 的提交模式）取用，主 Agent 选「合进需求分支」后先对需求分支最新 head 试合并，干净就把这一块 squash 成一个提交接在需求分支 head 上快进推送，有冲突交回执行者合并；`sync=true` 的块以执行者的合并提交快进；合入后删掉临时分支。squash 提交的说明带 `Coda-Piece: <运行 ID>`，重跑合入前先按它找，不会合入两次。输入改为由调用方给全：去掉 `lane`，加 `branch`（需求分支名）、`base`（目标分支，跟上目标分支时用）；输出只有 `commit`，放弃时以出错结束，调用方的出错边界接得到原因。监督开发、需求交付的任务文字与说明跟着改说法。

插件只返回补充，不改正文、附件、引用或输入框的执行者。多个模式的补充由 Coda 合并，`tell` 是字符串数组，按列表追加后随这条发送到每个收到它的会话；只要有一项 `divert: true` 就不发给默认去向，各模式追加的去向仍分别执行。

| 模式 | 发出的一条的补充 |
| --- | --- |
| 交接 | `divert: true`，追加 `thread` 去向，带 `handoffSource`、可选 `agent`、`open: true` |
| 子会话 | `divert: true`，追加 `thread` 去向，带 `handoffSource`、`parentThreadId`、`replyTo`、可选 `agent`、`open: true` |
| Ultra | 创建新会话（交接、子会话、默认去向为新会话）时返回完整开启说明；已有会话里，仅当状态标记要给完整说明（首次、改名单）时返回，其余返回 `null`；压缩后的说明由 watch 立即给（见「Ultra 用法」） |
| 循环 | `divert: true`，追加 `loop` 去向，带 `thread`、`every` |
| `!` | `divert: true`，会话中追加 `message` 去向，带 `thread`、`run: true`；新任务中追加 `thread` 去向，带 `run: true`、`open: true` |

新会话去向明确跳转，客户端按每项 `open` 执行。Coda 将非一次性、非触发式且适用于会话的模式和参数写入新会话输入框；各会话只为自己实际收到的模式消息计数，转发到新会话不增加来源的 `sent`。空 Agent 不写入目标，交由 Coda 沿用 `spec.agent`（包括 settings）。

## 循环用法

在已有会话的输入框里打 `/loop`，填写每轮要做的事，选择周期后点「开始循环」。周期默认 30 分钟，可选 5 分钟、10 分钟、15 分钟、30 分钟、1 小时、2 小时、3 小时、6 小时、12 小时或 1 天。

这条消息就是第 1 轮；Coda 收下后创建循环，输入框随即退出循环模式。每轮做完才开始计算下一个周期，不叠着跑；7 天后自动结束，也可提前停止，归档会话同样结束循环。计时与重发由 Coda 后端负责，会话进程被回收后仍会按时恢复。

循环的计时行为沿用 [Coda #2051](https://github.com/coda-console/coda/pull/2051)，3.0.0 通过上述 `loop` 去向提交。

## Ultra 模板设置改名

Ultra 的模板设置由 `ultra.templates` 改为 **`composer.templates`**，模板的数据结构不变。清单的预设只引用新设置名，由 Coda 按输入框所在目录读取。
旧 Ultra 包暂时保留，旧设置迁移和卸载旧插件由 [Coda issue #2050](https://github.com/coda-console/coda/issues/2050) 的第 4 步处理，本插件不自行迁移。

## Ultra 用法

在会话或新任务输入框打 `/ultra`，点模式条选择执行者名单；点 × 退出。单独开启时消息照常发给当前会话，与其他模式一起开启时按各模式的去向发送。
Ultra 只管派活：主 Agent 定任务、处理困难决策、审查别人交回的东西；不改代码的调研、排查和核实用 Coda 的 `spawn` 交给名单里的执行者，按任务挑。
它不规定代码怎么改、走不走开发流程：开发流程由你在输入框「＋」里开启，或由 Agent 用 `workflow_run` 带 `confirm: true` 填好、你在开工卡上确认，它的规则写在交给主 Agent 的任务里。

`composer.templates` 是执行者模板，一行「模板名、Agent、什么时候派给它」。同一模板名的行是一组，进入时填第一组；默认没有模板。
Ultra 参数仍保存为 `subagents`，预设引用 `{ "from": "composer.templates", "by": "template" }`，选择预设只填入名单一次，之后可修改。
派活时任务书要自成一体：目标与它服务的决定、已知或已排除的、范围与不要碰的、去哪里找、交回什么（先结论，再来源和实际证据）。
结果不好时按原因处理：任务书漏了的，补写后发回同一会话；只有说法没有证据的，向同一会话要证据；任务书清楚但结果不对的，换名单里的另一项；会话中断或工具失败的，重试；不要自己悄悄重做。
名单管所有为委派的工作选 Agent 的地方：Coda `spawn`，以及流程里要 Agent 的输入，都按任务从名单选，传 `agent`、`model`、`effort`、`mode`、`options`；只有名单为空或没有条目适合时，才用当前会话的 Agent 和模型。提示不点名具体流程和输入，也不讲开发流程怎么走。

会话输入框开着 Ultra 时，完整说明只在下列情况给一次，平时不发提醒：

- 首次生效、名单改过：输入框的变化只更新插件内存里的状态（名单、`sent`、`compactions`、是否要给完整说明），不 `tell`，免得用户在界面上改名单时连发。说明随下一条用户消息（`coda/submission@1` 参与者，已有会话里返回完整说明并清掉标记，否则返回 `null`；创建新会话时照旧返回完整说明）或下一轮结束（`coda.watch('threads')` 里 `turn` 由非空变 `null`，用 `coda.tell` 追加）给出，两处只会给一份。空闲时连着改几次只给最新名单的一份。
- 压缩：`coda/composer@1` 的 `status.compactions`（非负整数，缺省按 0 计）变大就是压缩，每次压缩加 1；插件立即用 `coda.tell` 给完整说明，不等一轮结束或下一条消息，不论当时是否在跑一轮，并清掉待给标记。两次压缩之间没有用户消息（`sent` 一直是 0）也都识别。只看 `compactions`，不从 `sent` 由大于 0 变 0、内容或用量推断。

怎么认新会话：带着 Ultra 新建的会话，输入框与第一条在同一个事务里写成 `sent=1`，第一条已带完整说明；刚进入 Ultra 时 `sent=0`，给完整说明；插件重启后重放的输入框当作首次（重启后会多给一次），`compactions` 只记基线，不算压缩。
新任务输入框（`new:…`）本身不发说明，它创建的会话照上面处理；未开 Ultra 的会话不发。状态只放内存。

6.2.0 起 Ultra 每轮提醒（原来按用户发出的消息每 10 条一次，长程任务里会话多半被流程结果叫醒，计数不动，压缩后名单也丢了）；10.3.0 起去掉每轮提醒，改为只在首次、改名单和压缩后给完整说明，压缩由 `status.compactions` 识别。
并发已满就等名额；spawn 不可用就报告阻塞，不改用原生子 Agent。用户的明确指令优先。
5.0.0 起 Ultra 不再要求「所有代码修改都通过 develop」，也不再讲 develop、deliver 的用法；两个流程改为由你在会话里开启，或由 Agent 发起「开工」后你在开工卡上确认，develop 的执行者从 `agent`、`model`、`effort`、`mode` 四个参数换成一个 `executor`（Coda #2303）。需要支持流程参数 `agent` 类型（协议 3.5.0，Coda #2332）、`coda:wake` 与 `note="required"` 的 Coda，不能用于旧版。

插件声明 `activationEvents: ["onStartupFinished"]`，重启后通过 `coda.watch('threads', …)` 与 `coda.watch('coda/composer@1', …)` 恢复观察。
Ultra 消失时，若这个会话收到过说明（submission 投递过或 watch 告诉过；重启后不知道时按 `sent > 0` 判断）就用 `coda.tell` 告知关闭一次，恢复通常的执行与委派规则；没收到过就不说。
名单连同说明超过 Coda 单次告诉 Agent 的 4000 字上限时，缩短名单再发。这些分工是提示词约束，不在运行时禁用工具。

## 监督开发

一个需求开一次「监督开发」（`develop`），对应一条需求分支 `lane/<运行 ID>`。和主 Agent 把需求聊清楚后，在输入框「＋」里开启它，或由 Agent 用 `workflow_run` 带 `confirm: true` 填好、你在开工卡上确认。
中间的事都由主 Agent 负责：它用「块」（`piece`，见下一节）把需求一块块交给执行者，每一块经项目检查、评审和它的审查后合进需求分支，这期间不找你；
它判断需求做完后「提交验收」，需求分支先跟上目标分支，才开 PR 进目标分支，经检查、整体评审（小问题先交开工执行者就地修）和设备验收后，由你批准一次，用合并提交合并，再运行你勾的合并后流程。
它是手动流程，不订阅 PR 事件，也不依赖 review 插件（评审按名字调用能力 `review-commit`）；它开的 PR 不会启动 PR 生命流程（见下文「不触发 PR 生命流程」）。

| 输入 | 用途 |
| --- | --- |
| `title` | 需求名（也是 PR 标题），默认空。目标与完成标准是发起时带的需求文字（`run.message`：「＋」或开工卡上的需求、`workflow_run` 的 `message`）；需求名和它缺一样时由主 Agent 写 |
| `devices` | 布尔值「设备验收」，默认关；改了客户端、要在 Mac 或 iPhone 上验收时打开 |
| `device` | 可选文本「验收设备」，如 `duo-testbed`，默认空；开启设备验收且非空时，从安装前到验收结束独占这台设备；留空不占设备 |
| `hold` | 可选文本「验收时占用」，一个组名，默认空；开启设备验收且非空时，安装与验收期间另外占着这个组（容量 1），如项目的需求分支专用后端；留空不占 |
| `delivery` | 字符串「所属需求交付」，填需求交付（`deliver`）运行的 ID；默认空，为独立交付 |
| `executor`、`executor2` | 「执行者」「备用执行者」，各是一组 Agent 选择（流程参数的 `agent` 类型），没有默认值，不填就是空（`null`）；是本需求分支里块的默认人选：主 Agent 派每个块时把它们原样传给 `piece` 的 `executor`、`executor2`，没理由另定的块用它们，难的或性质不同的块可按块另定；不填则每块自己定。「需求进行中」任务里把开工值以 JSON 写出来，主 Agent 可直接复制 |
| `reviewer`、`reviewer2`、`reviewer3` | 「整体评审者」「第二整体评审者」「第三整体评审者」，各是一组 Agent 选择（流程参数的 `agent` 类型），没有默认值，不填就是空（`null`）、不评；见下文「整体评审」 |
| `base` | 「目标分支」，留空从 GitHub 读取仓库默认分支 |

0. 需求名（`title`）和需求文字（`run.message`）缺一样时（如你直接在会话里开启的），先交主 Agent「写需求」：这张任务不叫醒它（`coda:wake="false"`），随你在会话里的下一条消息告诉它，说明你开启了监督开发、它要做什么；发起时带了需求文字就一并写在任务里。两样都有时（如开工卡确认的、需求交付发起的）不经过这张任务。主 Agent 答复时备注必填：第一行是需求名，空一行后是目标与完成标准；缺一样回到这张任务。
1. **建需求分支**：从远端目标分支的最新提交建 `lane/<运行 ID>` 并推送，分支名只用 ASCII。远端已有同名需求分支时沿用它，不重建：运行从头重跑时不会因为分支已存在而失败，也不会丢掉已合进需求分支的改动。
2. **需求进行中**：交主 Agent 一张「需求进行中」任务，可以挂好几天。任务里写着需求、目标、需求分支，以及怎么推进：
   - 每一块用 `workflow_run` 发起一个块：传 `branch`（需求分支名）、`base`（目标分支）、`title`、`task`，以及这一块的 `executor`、`executor2`、`reviewer`、`reviewer2`。`executor` 必传（`piece` 不再落到发起会话）：没理由另定的块传开工执行者，难的或性质不同的块按执行者名单（有的话）另定；`executor2` 同理，开工值有就默认传它；开工没填时每块自己定；`reviewer`、`reviewer2` 仍由主 Agent 按这一块的性质逐个定；
   - 互不依赖的块可以同时发起，有依赖的等前一个合进需求分支再发起；
   - 跟上目标分支用 `sync=true` 的块；
   - 中途想先看效果，可以用需求分支的提交发起 `mac-preview-install`、`ios-preview-install`，或对需求分支 head 跑一次合并前检查（加入挂点 `premerge` 的流程）。

   答复有三种：
   - 「提交验收」：备注必填，是写给你的改动汇报（做了什么、需要你知道的风险或没做的），放在批准卡和 PR 描述最上面，每次提交以最新一份为准；进入收尾。
   - 「暂停」：备注必填，写为什么停、等什么。转成你手上的「需求已暂停」卡，卡上是这段备注；你选「继续」回到「需求进行中」（附言随原因交给主 Agent），选「放弃」结束。这样主 Agent 不会每次空下来又被叫醒。
   - 「放弃」：结束这次运行，需求分支保留。

   必填备注没写（含只写空白）时回到同一张任务说明缺什么。每次回到「需求进行中」，任务里都写着回来的原因：检查失败的运行与步骤、设备验收的意见与截图路径、你暂不合并的原因、整体评审后主 Agent 的说明等；主 Agent 派修复用的块，再重新「提交验收」。
3. **跟上目标分支**：先让需求分支跟上目标分支（下文「提交验收时跟上目标分支」），有冲突且没填开工执行者、或推送被拒时带着原因回到「需求进行中」。
   **开 PR**：开或更新需求分支进目标分支的 PR，标题是需求名。正文依次是主 Agent 最近一次「提交验收」的汇报、合进需求分支的块列表（标题与链接，按编号先后）、流程直接推到需求分支的提交（跟上目标分支的合并提交、整体评审的修复提交，有才列）、改动区域统计（下文「改动区域」），合称汇总，批准卡和待交付卡贴的就是它（整体评审只有 P3 时再加上没修的 P3）。
   块列表用 `gh pr list --base lane/<运行 ID> --state merged` 从 GitHub 读；已开着的 PR 也用 `gh pr list --head lane/<运行 ID> --state open` 从 GitHub 找。需求跨好几天，从头重跑时只重建收尾，不靠运行暂存。
4. **检查**：独立交付开了设备验收（`devices=true`、`delivery` 留空）时，开 PR 后与检查并行调用项目加入挂点 `prebuild` 的（预编）流程，传需求分支 head，填了 `device` 时另传 `device`；它为随后验收要装的客户端先编好，检查不等它，它失败只留在调用记录里，安装流程到时照常自己构建，项目没有这类流程时立即结束。项目检查已在各块上跑过；需求分支 head 是本运行已通过检查的同一提交时复用，否则在它上面跑一次挂点 `check`。随后在需求分支 head 上跑一次挂点 `premerge`（合并前检查，放每个版本都跑嫌贵的验证），再等 GitHub 检查：核对 PR 的 `headRefOid` 与需求分支 head 一致，每 10 秒查询一次检查，最多等 120 秒登记；出现检查后用 `gh pr checks <PR> --watch` 等全部结束，并再次核对 head。连续 120 秒为空才按无 CI 通过，日志明确记录这一判断（有界等待是为了兼容 GitHub Actions 和外部 CI，不猜测 workflow 的事件、路径或分支过滤；超过窗口才登记的 CI 不在保证范围内）。任何一项失败都带着运行链接回到「需求进行中」，主 Agent 用 `workflow_status` 读失败的流程、步骤和日志。
5. **整体评审**：填了整体评审者时，对整条需求分支评一次（下文「整体评审」）：只有 P3 或没有发现直接往下走；只有测试、文档、风格类的 P2 时先交开工执行者在需求分支上修、原评审者复评；其余交主 Agent 选「继续验收」或「回到进行中」。都不填就跳过。
6. **设备验收**：`devices=true` 且 `delivery` 留空时进入「安装与设备验收」段。主 Agent 用 `workflow_run` 带需求分支 head 的精确 `commit` 只安装改到的那一端（`mac-preview-install`、`ios-preview-install`），发起的安装都成功后答复「已装好」；要先修改时选「回到进行中」，备注必填，缺少时返回安装卡。随后你答复「设备验收」，「不行」必须附言（写意见或附截图，`note="required"`），意见与截图路径带回「需求进行中」。改了后端、项目允许从需求分支部署后端时，主 Agent 按项目的说明同样带需求分支 head 发起后端部署；填了 `hold` 时本段占着那个组（下文「设备占用」）。验收通过后流程用 `tell-session` 告诉主 Agent，接下来等你批准。
7. **批准**：`delivery` 非空时进入给主 Agent 的「待交付」（见下文），不出你的批准卡。否则先在需求分支 head 上列出加入挂点 `merged` 的流程（`hook-joiners`），你在「批准合并」卡上决定：卡上只有汇总、已通过的检查（含整体评审、设备验收）和 PR；「合并」的勾选项是这些流程（下文「合并后的流程」），之后是「全部完成后通知 Agent」，默认勾选。「暂不合并」必须附言，原因带回「需求进行中」交给主 Agent 跟进。批准后直接合并，不再跑检查。
8. **合并**：用合并提交合并：`gh pr merge --repo <host/owner/repo> --merge --match-head-commit <需求分支 head> --delete-branch`。目标分支的 first-parent 历史里每个需求一个提交（按 first-parent 计数的构建号照常算），需求分支里每个块一个提交，可以二分、可以单独回退。
   合并前查询 PR 状态：已合并且 head 与本次记录一致时直接输出原合并提交；已合并但 head 不一致或已关闭未合并时明确报错。合并命令失败后查询一次 PR，仅在仍 OPEN 且 `mergeable=CONFLICTING` 时带着原因回到「需求进行中」：主 Agent 发起 `sync=true` 的块把最新目标分支合进来、解冲突、顺延撞号的迁移版本，再提交验收；之后重新跑检查、出新的批准卡，合并后的流程以新卡为准。其余合并失败保留原退出码，不依赖错误文案判断冲突。仓库从 PR URL 取得，gh 只删除远端需求分支、不操作本地分支，支持分离 HEAD 检出，也兼容 GitHub 合并后自动删除分支。
   成功后运行你勾的合并后流程（下文「合并后的流程」）；一个都没勾，或勾了的都被选了「这一项这次不跑」，就结束。

「全部完成后通知 Agent」控制最外层结束事件的 `coda:notify`：取消勾选后，合并及所选合并后流程全部成功时不叫醒发起会话，只在下一轮顺带告知结果；失败仍叫醒。依赖 Coda #2107 的结束通知支持。

`delivery` 非空时（成员需求运行，由需求交付发起），检查和整体评审之后进入给主 Agent 的「待交付」，跳过安装和设备验收，不受 `devices` 影响。任务列出所属需求交付、PR、head、需求分支和汇总：

- 「退回修改」备注必填，缺少则返回待交付；意见带回「需求进行中」，派一块修好后重新提交验收、跑检查，再回到待交付。
- 「放行合并」由主 Agent 按需求交付运行的顺序选择，随后以合并提交合并（合并前检查已在待交付前跑过）；合并成功输出合并提交并结束，仍通知发起会话，不运行合并后的流程（由需求交付统一运行）。

运行之间只通过主 Agent 答复各自的人工任务协调，不直接发消息，也不依赖跨仓库原生子运行。反馈与汇报暂存于 `$CODA_ARTIFACTS/develop.json`；长期结果在需求分支、块与进目标分支的 PR 里。

### 挂点

监督开发与块调用的项目流程都按挂点找（Coda 的 `docs/workflows.md`「调用其他流程」），本插件不认识任何一类。参数都是 `commit`（要检查的提交）：

| 挂点 | 谁调用 | 怎么跑 |
| --- | --- | --- |
| `check` | 块每次交付、监督开发提交验收（需求分支 head 没通过过时） | 全部运行并等结束，有一个失败就算没通过 |
| `premerge` | 监督开发提交验收，弹出批准卡之前 | 同上 |
| `prebuild` | 监督开发提交验收，独立交付开了设备验收时 | 全部运行，不等、不管成败；另传 `device`（填了时） |
| `merged` | 批准卡（下文「合并后的流程」） | 只跑勾了的 |

`develop` 自己加入挂点 `develop`：Coda 在「＋」和开工卡上列出加入这个挂点的流程作为开发流程。

### 合并后的流程

监督开发与需求交付声明挂点 `merged`：合并后要做的事（部署、发布预览版、发布正式版……）不写在流程里，由项目自己的流程（或启用插件的流程）用 `<coda:join hook="merged" …/>` 加入（Coda 的 `docs/workflows.md`「调用其他流程」）。约定：

- **加入者带什么**：`name` 是卡上勾选项的名字（不写用流程名），`detail` 一行说明，`default` 是否默认勾（不写为不勾，默认不勾就由加入者这样表达），`order` 排序（小的在前，不写排最后），可选 `inputs`：它要从卡上拿的自己的文字参数（本流程 `type` 为 string 的 `coda:input`，标签取参数的 `label`），如发布说明 `notes`。
- **卡上**：批准前用 `hook-joiners`（`hook=merged`，`commit` 是要批准的 head）列出加入者，作为「合并」的勾选项（`coda:optionList`），你可以勾任意几个；勾上带 `inputs` 的加入者时卡上出现对应的输入框（几项要同一个输入只出一个）。
- **合并后**：在合并提交上用 `run-workflows`（`hook=merged`，`only` 是勾了的流程名，`commit` 是合并提交，`inputs` 是卡上写了的文字）运行勾了的，等它们都结束；一个没成功这一步就失败。每个加入者只拿到它自己声明的参数。没勾任何一个就不调用。
- **卡上没写的文字**：勾了的加入者要、卡上没写的输入，合并后先交主 Agent「填写合并后流程要的文字」，每个输入一张（依次），任务里写明是哪一项、哪几个流程要；主 Agent 按这次合并进来的改动写面向用户的文字，「已写好」的备注必填（`note="required"`），只附文件没写字时「整理合并后流程的参数」失败并写明是哪一项。选「这一项这次不跑」（备注可不写）是这段文字不写：「整理合并后流程的参数」把所有勾了且要这段文字的加入者（几个加入者共用一段文字，如预览发布与正式发布都要 `notes`，就全部）从 `only` 里去掉，输出新的 `only` 交给 `run-workflows`，其余勾了的照常运行；新的 `only` 为空就不调用 `run-workflows`，监督开发直接结束，需求交付直接进入真实环境验证。
- 成员需求运行（`delivery` 非空）不列出、不运行，由需求交付统一运行。

### 提交验收时跟上目标分支

「提交验收」之后、开 PR 之前，「跟上目标分支」（`sync-base`）在步骤工作区 fetch 目标分支（`base`，留空为仓库默认分支）和需求分支，固定两端提交，按情形处理：

| 情形 | 做法 |
| --- | --- |
| 需求分支已包含目标分支 | 不动 |
| 需求分支是目标分支的祖先 | 把需求分支快进到目标分支 |
| 分叉、能干净合并（`git merge-tree` 试合并） | 在步骤工作区做一个保留双亲的合并提交（需求分支在前、目标分支在后），推到需求分支 |
| 有冲突，填了开工执行者 `executor` | 「执行者合并目标分支」（`sync-resolve`）：从固定的需求分支 head 新开执行会话，把固定的目标分支提交合并（merge，不变基）进来、解冲突、顺延撞号的迁移版本、提交合并提交；它的 head 同时包含两端时由流程推到需求分支，否则带着它的回答回到「需求进行中」 |
| 有冲突，没填开工执行者 | 带着冲突的文件回到「需求进行中」，主 Agent 照旧发起 `sync=true` 的块|

推到需求分支都是普通推送（不 force）。被拒且需求分支已经不是固定的那个提交（被别的提交推进了）时不重试、不覆盖，带着原因回到「需求进行中」；需求分支没动的推送失败保留原退出码。
之后新 head 照常开 PR、跑全部检查（项目检查、合并前检查、GitHub 检查），不跳过；合并提交和执行者解冲突的提交列进汇总的「流程直接推到需求分支的提交」。最后合并时目标分支又变了、冲突了，仍按上文第 8 步回到「需求进行中」。

### 整体评审

填了 `reviewer`、`reviewer2`、`reviewer3` 中任何一个时，GitHub 检查通过后先「确定整体评审范围」（`overall-round`），再进入子流程「整体评审」（`coda:optional`，只在走进去时出现在卡片上）：三个位置各一份、同时进行，没填的直接结束、记为跳过；
填了的用 `callActivity calledElement="review-commit"` 按名字调用评审能力，完整评审时 `base` 是目标分支的最新提交、`head` 是需求分支 head（评的是两者的三点 diff，即整条需求分支）、`task` 是需求名、目标与完成标准和主 Agent 的汇报、`evidence` 是项目检查结果并注明合并前检查与 GitHub 检查已通过。
评审没完成时 `review-commit` 照常结束（`decision` 为 `INCOMPLETE`），调用本身没成时出错边界接住，都照常结束、不重试。

评审之后「分流整体评审意见」（`overall-triage`）用 `scripts/triage.mjs` 的 `triageOverall` 分流。它和块的 `triage` 用同一本发现账（编号、复评结论、新发现接着编号的规则都相同，见下文「评审收敛」），只是路由按严重程度与类别（`kind`），不看 review 设置的阻塞级别：

| 情形 | 去向 |
| --- | --- |
| 有位置没评成（调用没成，或 `INCOMPLETE`），或评的不是当前需求分支 head | 主 Agent 的「整体评审结论」 |
| 有 P0、P1 | 同上 |
| 有任何级别的 `contract`、`scope` 类，或类别不是 `test-quality`、`documentation`、`style` 的 P2（含 `correctness`） | 同上 |
| 执行者反驳（`disputed`）的发现评审者仍坚持 | 同上 |
| 有 P2、全是 `test-quality`、`documentation`、`style` 类：没填开工执行者，或已自动修满两轮 | 同上 |
| 有 P2、全是这三类，其余情形 | 交开工执行者在需求分支上修（「执行者修整体评审的小问题」，`overall-fix`） |
| 只有 P3，或没有发现 | 不出主 Agent 的卡，直接进设备验收、待交付或批准；没修的 P3（编号、类别、标题、位置、说明）写进 PR 描述，批准卡和待交付卡的汇总也带上 |

`overall-fix` 把没关的 P2 交给开工执行者，写法同块的「执行者处理评审意见」：第一轮从需求分支 head 新开执行会话，之后续同一会话（`--continue`）；执行者只提交，逐条回 `fixed` 或 `disputed`（`responses` 代码块）。之后：

- 有新提交：流程普通推送到需求分支（被拒同上文，回到「需求进行中」），回到「开 PR」：汇总列出这些修复提交，新 head 照常跑全部检查，再增量复评：每个原来的整体评审位置重新调用 `review-commit`，`base` 是上次评过的 head，`previous` 带这个位置还没关的发现与执行者的回应，回到分流；
- 没有新提交、只有反驳：不重跑检查，直接复评（`base` 与 `head` 相同），回到分流；
- 既没有新提交也没有反驳：交主 Agent。

主 Agent 收到「整体评审结论」之前经过「整理整体评审的收敛经过」（`overall-rounds`）：卡上列出最后一轮每位的结论与发现（写法与块审查卡上的「评审者的发现」相同，原文在 `$CODA_ARTIFACTS/reviews.md`，卡上给出路径），再附收敛经过（全文在 `$CODA_ARTIFACTS/converge.md`，过长时卡上只放最后一轮）。发现成不成立由它判断：选「继续验收」往下走；选「回到进行中」时备注可选，连同评审原文的路径带回「需求进行中」，主 Agent 派一块修好后再提交验收。每次提交验收收敛都从头开始（状态在 `develop.json` 的 `converge`）。

需要 review 插件 3.4.0 及以上（发现带 `kind`，`review-commit` 收 `previous`、输出 `resolutions`、`blocking`）。10.0.0 及更早开工、仍在跑的运行按开工时的定义走：提交验收直接开 PR、整体评审结果都交主 Agent，它们用的动作都还在。

### 改动区域

PR 汇总的改动块统计目标分支最新提交与需求分支 head 的三点 diff（与 GitHub PR 的 Files changed 一致），按区域列出文件数和增删行数，区域按增删总行数从多到少排。改名按新路径归类，二进制文件计入文件数、行数记 0。

区域由需求分支 head 上的 `.coda/areas.json` 声明，格式为 `{ "区域名": ["路径前缀", ...] }`，前缀是普通字符串前缀，如 `iOS/`、`Sources/CodaCore/`、`AGENTS.md`。一个文件归入最长匹配前缀所在的区域；都不匹配时归到它的顶层目录名，根目录下的文件归「根目录」。没有这个文件时全部按顶层目录归类；文件存在但 JSON 写坏时开 PR 步骤直接失败。

### 设备占用

填写 `device` 且开启设备验收时，安装前先调用 testbed 的 `resolve-testbed` 按设备名解析，再用 `hold-group` 占用返回的组（容量 1），状态显示「等验收设备 <设备名>」。引擎按组归属在整个空间排队；composer 不新增 testbed 硬依赖；填写设备名使用验收时须安装 testbed。安装与验收共用这一段占用，发起 `ios-preview-install` 时除精确 `commit` 外还传同一个 `device`，安装运行借用本段设备，不另排队。通过、回到进行中或取消并收尾后释放；再次进入重新排队。缺少必填意见时仍留在本段补填。未填设备名时不传设备参数、不占设备。

填写 `hold` 时，占完验收设备之后再用 `hold-group` 占着这个组（容量 1），状态显示「等 <组名>」；先设备、后这个组，顺序固定，两条运行不会互相等住。它给项目里同一时间只能给一个需求用的东西，如只有一台的需求分支专用后端：项目的部署流程整条运行占着同一个组，主 Agent 在安装卡上发起的部署借用本段的组直接进，别的运行（如别的需求合并后的部署）排在本段之后。组名和要发起哪个流程由项目自己说明，composer 只照传的组名占。和设备一样，离开本段就放开，再次进入重新排队；留空不占。

### 不触发 PR 生命流程

流程步骤替运行所属的会话说话（`CODA_THREAD_ID`），GitHub 插件的 `gh` 会把它 `gh pr create` 开的 PR 报给「PR 观察」，PR 观察再发布 `pull_request.opened` 等事件，review 插件的 PR 生命流程（`pull-request`）就会自动跟上同一个 PR：
它会再跑一遍检查、评审，进目标分支的 PR 还会再出一张批准卡。所以监督开发开 PR 时去掉 `CODA_THREAD_ID`（`scripts/shared.mjs` 的 `openPr`），这个 PR 不上报，PR 观察和 PR 生命流程都不会因它启动；检查、评审、合并都由开它的流程自己做。
代价是这个 PR 不在会话的「报过的 PR」里（GitHub 插件的 `github-reported-pr` 找不到它），要手动评审时直接传 PR 地址。

## 块

「块」（`piece`）是需求运行里的一项改动：主 Agent 在「需求进行中」用 `workflow_run` 发起，执行者写代码，经项目检查、评审和主 Agent 的审查后合进需求分支，结果交回发起的会话。
它不开 GitHub PR：一个需求在 GitHub 上只有需求分支进目标分支的那一个 PR。它也不出你的卡片、不装机、不部署、不跑合并前检查（这些只在需求分支进目标分支时做一次）。一项就是一块，下一项另起一块；互不依赖的可以同时跑。
块需要的都由输入给出，不按需求运行 ID 去查。

| 输入 | 用途 |
| --- | --- |
| `branch` | 必填，需求分支名；执行者从它的 head 开工，这一块合进它 |
| `base` | 必填，目标分支（需求最后合进的分支）；`sync=true` 的块把 `origin/<base>` 合并进来 |
| `title` | 必填，也是合进需求分支那个提交的标题 |
| `task` | 必填，自足的任务书：背景、范围与验收要求 |
| `sync` | 布尔值「跟上目标分支」，默认关；见下文「跟上目标分支」 |
| `executor` | 必填「执行者」，一组 Agent 选择（Agent、模型、强度、模式与其他选项，流程参数的 `agent` 类型），通常是所属监督开发的开工执行者；没有默认值，不传时启动就报「需要参数 executor」，不再落到发起会话。没选的模型、强度、模式用执行者的默认值，其他选项逐个传给 `coda-agent --option` |
| `executor2` | 「备用执行者」，没有默认值，不填就是空（`null`）；见下文「备用执行者与退回次数」 |
| `reviewer`、`reviewer2` | 「评审者」「第二评审者」，没有默认值，不填就不评；填了的评每一次交付，见下文「评审」 |

1. **执行**：用 `coda-agent --commit <需求分支当前 head> --json` 开执行会话。固定说明要求遵守 AGENTS.md，只做本项、在当前分支提交、不推送、不写防御性或冗余代码、不顺手重构；只跑与改动直接相关的快检查，流程会在审查前自己跑项目检查，构建、全套和界面检查不重复跑，不必再用 run-held 跑整套编译；只跑改动直接涉及的测试文件，不跑无文件参数的 `check.sh backend`、`--all`、完整 workflows 套件、客户端编译（任务明确要求的除外）；验证命令要把原始检查的退出码传出去（直接执行检查命令，要看日志尾部就用 `rc=0; <检查> > "$log" 2>&1 || rc=$?; tail -n 80 "$log"; exit "$rc"`：run-held 在 zsh 里执行，`status` 是 zsh 的只读变量，不能用作变量名；不能只 echo 退出码，不能让最后的 tail / grep / cmp 决定成败）；改坏验证只跑命中的那个用例、沿用默认时限，挂住了先定位原因；run-held 和流程运行的结果会自己送回，不另起 Monitor 或后台任务盯日志；并报告实际验证。
   执行者的分支/head 必须在本机仓库可读；`coda-agent --json` 标准输出是一行 `{session, branch, head, answer}`，`--continue` 保留同一会话并遵守首次的退出码约定。
   执行步骤失败后恢复（`workflow_resume`）或重试再跑时接回这一步已开的会话：会话失败、取消或结果未知时 `coda-agent` 仍在标准输出给出会话 ID，流程在 `$CODA_ARTIFACTS/piece.json` 的 `opening` 里完整记下待完成的动作：`action`（`execute`、`swap` 或 `revise`）、`text`（任务文字）、`agent`（这个动作该用的执行者配置：`execute` 用当前执行者（首次执行还没有 `executor` 时用 `executor` 参数），`swap` 用备用执行者，`revise` 用当前执行者）、`session`（有会话才有）。动作开始前就写入，拿到会话 ID 后补上；只有动作成功才清掉并把会话写进 `executor`，中途怎么失败都不清。再跑时有 `session` 就用 `--continue` 发一段续跑说明——先核对现场（`git status`、`git log`、上次做到哪），再接着完成原任务，不要从头重做——后面附任务书；没有就用 `opening.agent` 从需求分支 head 新开。步骤被杀或后端重启而没拿到标准输出时记不下会话 ID，只能新开。运行从头重跑（插件更新后恢复时流程定义变了，会从开始事件重走）时 `execute` 以上一次的完整状态为底（状态文件已在），只重写自己的输入（需求分支、目标分支、临时分支、标题、任务、是否跟上目标分支），其余原样保留（`opening`、`executor`、当前执行者配置、检查失败计数、退回次数等），首次开工才新建：有 `opening` 就做它描述的那个动作（不管是 `execute`、`swap` 还是 `revise`），换人的决定和备用会话已做的提交不会被吞掉；没有 `opening` 才用 `--continue` 接回 `executor.session`，同样先发续跑说明，不再从需求分支 head 另开会话、推翻已审查的提交；换过备用执行者后当前执行者（状态里的 `agent`）就是备用的，接不回时回退新开用的也是它，不因从头重跑退回流程参数里的原执行者；连续检查失败计数只在这次成功的会话是新开的（`--commit`）时清零，接回已有会话（退回修改、从头重跑、恢复）的不清；`swap` 没有 `opening` 时是有意新开，不在此列。「退回修改」本来接回同一会话，它失败后再跑（`opening` 记 `revise`）也先发续跑说明。`--continue` 接回的会话接不回时，Coda 侧的流程 Agent 步骤已在同一会话里续跑可恢复的失败，所以 `coda-agent` 失败就是终局，再按回复里有没有会话 ID 分两种：回复里没有 `session`（不管退出码；输出不是 JSON 也算）才算会话接不回，输出写明原因，只去掉 `opening.session`，同一次里用 `opening.agent` 和 `--commit <需求分支当前 head>` 新开会话、给原任务，新会话写回 `opening.session`，只回退一次；新开也失败时 `opening` 照样留着，下次重跑仍是同一个动作。回复里有 `session` 但失败（非零退出，或缺 `branch`、`head`）不新开：会话和它做出的提交还在，保留 `opening.session`（回复里的会话和记下的不同就改记回复里的），按失败退出，下次恢复继续 `--continue` 同一会话，不会被新会话的强推替换。退回修改接不回不新开：新开的会话没有已交付的提交和审查意见，修改必须在原会话里做，按失败处理并在输出里说明，记录留着。
2. **推送到临时分支**：把执行者的 head 强推到本运行的临时分支 `piece/<运行 ID>`，项目检查和评审从远端取得到这次交付；之后的交付推同一个分支。不开 PR。推送失败停在这一步，日志保留 Git 的具体原因；网络类失败（DNS、超时、连接重置、TLS、服务端 5xx）由 Coda 按 `coda:retry="3"` 自动再跑，同一个提交推同一个分支，重跑是幂等的。
3. **项目检查**：在这个 head 上跑项目加入挂点 `check` 的流程。失败时前两次自动交回同一执行会话，写明提交和本运行链接，由执行者用 `workflow_status` 读失败流程、步骤和日志；第三次连同三次记录交给主 Agent 审查，不评审。通过会清零连续失败次数。
4. **评审**：见下文「评审」；评审之后先分流，见下文「评审收敛」。
5. **主 Agent 审查**：列出执行会话、head 与它所在的临时分支、需求分支、看改动的命令（`git fetch origin <需求分支> <临时分支>` 后 `git diff origin/<需求分支>...<head>`）、退回次数、备用执行者、项目检查结果、执行者回答、评审者的发现和待处理反馈。答复有五种：
   - 「退回修改」：备注必填，同一个执行会话（`--continue`）继续修改。
   - 「让执行者合并需求分支」：备注可选；同一个执行会话把需求分支当前 head 合进来（见下文「合并需求分支」），不算退回。
   - 「换备用执行者重做」：备注必填；见下文「备用执行者与退回次数」。
   - 「合进需求分支」：见下文「合进需求分支」。
   - 「放弃」：删掉临时分支（已不在就跳过），需求分支不动，运行走到出错结束「主 Agent 放弃了这一块，需求分支没动」。

   必填备注没写时回到审查卡，「待处理反馈」里写明缺什么。审查要点、评审发现由主 Agent 判断成不成立，修改都交给执行者，主 Agent 不自己改代码。

运行结束时叫醒发起的会话（`coda:notify="true"`）。合进需求分支时正常结束，输出 `commit`：合进需求分支的提交（普通的块是 squash 得到的那个提交，跟上目标分支的块是执行者的合并提交）。
没合入就以失败结束，调用方拿得到原因：主 Agent 放弃时走出错结束，运行以「流程走到出错结束「主 Agent 放弃了这一块，需求分支没动」」失败；步骤失败没接住时以那一步的失败原因结束。用 `callActivity calledElement="piece"` 调它的流程在出错边界上接住（`CALL_FAILED`，原因随错误带上）。
执行会话与反馈暂存于 `$CODA_ARTIFACTS/piece.json`。

### 合进需求分支

主 Agent 选「合进需求分支」后，流程先 fetch 需求分支当前 head（别的块可能刚合进去），先认这一块是否已经合入，重跑这一步不会合入两次：
普通的块在需求分支里找说明带 `Coda-Piece: <运行 ID>` 的提交，找到就原样交出它；跟上目标分支的块看这次交付是不是已是需求分支的祖先。都没有才合：

- 普通的块用 `git merge-tree --write-tree` 试合并需求分支 head 与这次交付。只是试：不产生提交，不动任何引用、索引和工作区（只会在对象库里留下几个可回收的临时对象）；冲突时能按文件名列出。
  有冲突就不动需求分支，把下文的固定说明连同冲突的文件交给同一个执行会话合并（只合并，不变基），之后照常推送、检查、评审，再回到审查卡，不算退回。
  干净时把试合并得到的树做成一个提交（`git commit-tree`），父提交是需求分支 head，说明是 `title`、空一行、`Coda-Piece: <运行 ID>`：这一块不管执行者交了几个提交都是一个提交。再普通推送到需求分支，只快进、不强推；推送被拒（需求分支在这期间又动了）这一步失败，恢复时重新 fetch、重新试合并。
- 跟上目标分支的块（`sync=true`）不 squash：需求分支 head 是这次交付的祖先时，把需求分支快进到执行者的合并提交（不强推）；不是祖先时同样交回执行者先合并需求分支（能干净合并时不列冲突文件）。

合入后删掉临时分支（已不在就跳过）。

### 合并需求分支

「让执行者合并需求分支」和试合并发现冲突给执行者的是同一段固定说明：需求分支是哪一条、别的块可能已经合进去了，试合并时列出冲突的文件；要求先 `git fetch origin <需求分支>`，把它合并（不是变基）进当前分支——变基会改写已经审查过的提交；解决冲突，数据库迁移等版本号和需求分支撞号时顺延自己这边的；跑和冲突相关的测试后提交，只做这件事，回报冲突了哪些文件、各自怎么解决的、跑了什么；需求分支没有新提交时直接回报不需要合并。主 Agent 写了备注就附在后面。两种都不加退回次数。

### 跟上目标分支

需求分支活得久，目标分支动得快。主 Agent 专门发起一个 `sync=true` 的块，任务写把目标分支合进来、解冲突、顺延撞号的迁移版本。流程在任务书后附上固定说明：先 `git fetch origin <base>`，把 `origin/<base>` 合并（merge）进当前分支，不要变基、不要压成一个提交；它以合并提交快进进需求分支，保住需求分支与目标分支的祖先关系；迁移版本号撞号时顺延需求分支这边的。
合进需求分支时用快进而不是 squash：squash 会丢掉与目标分支的祖先关系，之后需求分支进目标分支时同样的冲突会再来一遍。

### 评审

评审在项目检查通过（「记录通过的检查」）之后、「整理审查材料」之前；检查没过不评，连续三次检查失败直接交主 Agent 审查的那条路也不经过它。
两个位置都没填时不进入评审。否则进入子流程「评审」（`coda:optional`）：两个位置各一份、同时进行（多实例），每份都走到自己的结束事件，两份都结束才往下走：

- 这一位没填：直接结束，记为跳过；
- 填了：`callActivity calledElement="review-commit"` 按名字调用评审能力，`base` 是需求分支当前 head（评的是三点 diff，别的块合进需求分支、或执行者合并了需求分支都不混进来）、`head` 是这次推送的提交、`task` 是任务书、`reviewer` 是这个位置、`evidence`（已有验证）是这次交付的项目检查结果；
  它和审查卡上「项目检查结果」是同一段文字（每个检查一行：流程名、结果、运行链接；项目没有声明检查流程时就是那一句说明），评审者不必再去 GitHub 找检查记录；传 `evidence` 需要 review 插件 2.17.0 及以上；
- 评审没完成（评审方会话重试后仍失败，或回复末尾没有合格的结论）：`review-commit` 照常结束，`decision` 为 `INCOMPLETE`，`line` 写明原因；不算这一步失败，免得几位同时评不成让运行「叫不动」；
- 调用本身没成（没有插件提供 `review-commit`、参数不合法；评审步骤到了 120 分钟时限也落在这里）：挂在调用上的出错边界接住，记为「没评成」，照常结束。两种都不重试、不换人。

「整理审查材料」只取评的是这次交付（执行者当前 head）的结果，审查卡在执行者回答之后多一段「评审者的发现」：每位一小节，写明是哪个位置、它的 Agent · 模型 · 强度、一句话结论，再列每条发现的严重程度、标题、位置和说明（标题、位置里的换行压成空格）；
评审没完成的写「没评成：」加原因，调用本身没成的写「没评成」并指向本运行里那一步（流程读不到被调用运行的失败原因，主 Agent 用 `workflow_status` 看）。没有评审时这一段不出现。
全部发现的说明与每位评审者的原文写在 `$CODA_ARTIFACTS/reviews.md`，卡上给出路径。卡片正文的 4000 字上限是协议对 BPMN 里 `documentation` 字面的检查，展开 `{{…}}` 后的文字不受它限制；这一段仍按 4000 字收着：放不下时卡上每条只留严重程度、标题和位置，说明在上面的文件里。

需要 0.3.32 及以上的 Coda（Coda #2435）：没填的评审者、备用执行者是空的 Agent 参数，按名字调用时要算作没传，旧版会让这次调用失败。

### 评审收敛

「确定评审范围」（`review-round`）在每次评审之前定怎么评：刚交执行者修过、等复评时是**增量复评**，否则是完整评审（`base` 是需求分支当前 head）。
评审之后、整理审查材料之前，「分流评审意见」（`triage`）给每条新发现一个固定编号（`reviewer:1`、`reviewer2:1`……，各位置接着编，之后几轮沿用，不靠标题匹配），再按 `scripts/triage.mjs` 的纯函数 `triage` 分流（监督开发的整体评审用同一本账、另一套路由 `triageOverall`，见「整体评审」）：

| 情形 | 去向 |
| --- | --- |
| 有位置没评成（调用没成，或 `INCOMPLETE`：`findings` 为空也不当通过） | 升级：主 Agent 审查卡 |
| 有位置评的 head（`review-commit` 输出的 `head`）不是执行者当前 head | 升级，这份结果拒收、不作数 |
| 执行者反驳（`disputed`）的发现评审者仍坚持（`upheld`） | 升级 |
| 还没关的发现里有 `contract` 或 `scope` 类 | 升级 |
| 有阻塞级发现，自动修已满两轮 | 升级 |
| 有阻塞级发现，其余情形 | 交同一个执行会话（`--continue`） |
| 都评完、没有阻塞级发现 | 主 Agent 审查卡，同原来 |

阻塞级别取 `review-commit` 输出的 `blocking`（即 review 插件的 `review.blockingSeverity`，默认 P2 及以上）。「执行者处理评审意见」（`address`）把没关的发现（编号、严重程度、类别、标题、位置、说明，阻塞级的标明）交给同一个执行会话，固定说明在前；执行者逐条回 `fixed`（附提交）或 `disputed`（附理由与证据），回复末尾用 `responses` 代码块结构化交回，不合格式的那条算没有回应，照样交评审者核实。之后：

- 有新提交：照常推送、跑项目检查（失败照旧自动续作，三次交主 Agent），再增量复评：每个原来的评审位置重新调用 `review-commit`（新会话），`base` 是上次评过的 head、`head` 是新 head，`previous` 带这个位置还没关的发现与执行者的回应；评审者对每条给出 `resolved`、`upheld` 或 `withdrawn`，也可以提新发现，回到分流。
- 没有新提交、只有反驳：不重跑检查，直接复评（`base` 与 `head` 相同），交原评审者确认，回到分流。
- 既没有新提交也没有反驳：复评不会有变化，交主 Agent 审查卡。

每次出审查卡之前经过「整理收敛经过」（`rounds`）：卡上在评审者的发现之后附收敛经过（每轮的新发现、执行者回应、评审者结论与分流结果；全文在 `$CODA_ARTIFACTS/converge.md`，过长时卡上只放最后一轮），之后不再等复评，主 Agent 退回、换人后的交付照常完整评审，自动修的轮数重新计。审查卡的答复不变，自动修不算退回。状态在 `piece.json` 的 `converge`。

### 备用执行者与退回次数

- 「换备用执行者重做」的备注写为什么换、接手的人要注意什么。流程用 `executor2` 从需求分支当前 head 新开一个执行会话，重做同一项：上一位没被接受的提交不带过来；这一步自己失败后再跑时接回这次新开的备用执行者会话，不再另开；给它的是固定的执行者说明、这一项的任务书原文、这次的备注，再加一句上一位执行者的分支与提交在哪里、可以参考也可以不用。
- 之后照常推送、检查、评审、审查。新会话连续检查失败的计数重新开始；再「退回修改」续的是新会话。主 Agent 可以再换一次，同样新开一个备用执行者的会话。换不换只由主 Agent 决定，流程不按退回次数自己换。
- 没填 `executor2` 时不能换。Coda 的流程方言只能按条件隐藏勾选项（`coda:option` 的 `coda:shown`），不能隐藏答复本身，所以这个答复总在卡上：卡上写着「备用执行者：未指定，不能换人」；选了就回到审查卡，「待处理反馈」里写明没有填备用执行者，运行不失败。

审查卡写「这一项已退回 N 次」，0 次也写。只有主 Agent 选「退回修改」（备注写了）才加一；项目检查失败的自动续作、换备用执行者、合并需求分支（两种都是）、备注没写回到卡上都不算；同一项换人不归零。

## 需求交付流程

一个需求跨几个仓库、要一起验收、一起批准时才用它；单仓库的需求直接用监督开发。在**交付并部署这个需求的项目**的会话里开启「需求交付」（`deliver`）：`title`（需求名）默认空，目标与完成标准是发起时带的需求文字（`run.message`），`devices`（是否设备验收）默认关，可选 `device`（验收设备名，如 `duo-testbed`，默认空），与监督开发的设备占用规则相同。

0. 需求名和需求文字缺一样时（如你开启的），先交主 Agent「写需求」，同样不叫醒它、随下一条消息告诉它。主 Agent 答复时备注必填：第一行需求名，空一行后是目标与完成标准。任务里写明之后怎么做：为每个要改的仓库在那里用 `workflow_run` 发起 `develop`（成员需求运行），传 `title`、`message`（这个仓库要做的部分与完成标准）、`delivery=<本运行 ID>`、`devices=false`，跨仓库用 `project`；主 Agent 在各成员的「需求进行中」用块把改动合进它的需求分支，做完提交验收，检查通过后停在「待交付」。

1. 主 Agent 在「确认达标」选择「开始交付」，备注每行一个成员 PR URL（各需求分支进目标分支的 PR），按合并顺序排列，被依赖的仓库在前。流程记录各 PR 的 URL、head、分支及 base；选择「放弃」结束。
2. 开启设备验收时，以最新 `origin/<base>` 创建 `delivery/<运行 ID>`（分支名只用 ASCII），按顺序 `git merge --no-ff` 仅合入本仓库成员的已记录 head 并推送。集成失败经错误边界回到确认，合并冲突的具体 Git 输出作为反馈。新一轮从最新 base 重新集成并替换本运行的预览分支。
3. 主 Agent 用集成提交只安装改到的那一端（`mac-preview-install`、`ios-preview-install`），发起的安装都成功后答「已装好」；「回到确认」须附原因。用户统一设备验收一次，「不行」须附意见并回到确认。主 Agent 在相关成员的「待交付」选「退回修改」，它回到「需求进行中」，派一块修好、重新提交验收并检查通过后再集成、安装、验收。`devices=false` 跳过集成、安装及设备验收。
4. 主 Agent 写约 15 行以内的交付汇报，备注作为批准卡正文：交付名、用户能感知的 3～5 条变化、结构变化（无则写「无」）、设备与检查结论、部署后真实环境验证计划、风险与未做事项（没有可省略）、PR 链接。不放执行者原文、测试数量、文件清单或代码。
5. 用户「批准交付」卡只显示汇报和全部成员 PR；「批准合并」的勾选项是本项目（本仓库最后一个成员的 head）上加入挂点 `merged` 的流程（见监督开发「合并后的流程」）。「暂不合并」必须附言（原因）并返回确认；设备验收的「不行」同样必须附言，可以只附截图，路径随反馈交回主 Agent。批准后进入「放行合并」。由任务叫醒发起会话，不再单独通知选择。
6. 主 Agent 按顺序放行成员，被依赖的仓库在前：先放行提供被钉版本的包的成员的「待交付」，等合并并发布新版本；再退回钉这些包的仓库成员，回到它的「需求进行中」派一块更新钉定的包版本，重新提交验收、检查通过后回到待交付；最后放行依赖方成员。成员都以合并提交合并。全部合并后备注写本项目最后一个合并提交，没有本仓库成员时写本项目当前目标分支提交。
7. 在该合并提交上运行勾了的合并后流程（卡上没写的文字先交主 Agent 补写，同监督开发「合并后的流程」）。随后主 Agent 按目标走真实环境验证，选「通过」或附具体意见选「有问题」，用 `tell-session` 告知发起会话后结束。一个都没勾，或勾了的都选了「这一项这次不跑」时，仍验证当前真实环境，备注说明没有部署造成的未验证部分；验证说明与告诉发起会话的结论里说的合并后流程，按实际运行的（跳过之后的 `only`）算，不按批准时勾的。

必填备注缺少时回原任务补填。成员快照、轮次和反馈保存在 `$CODA_ARTIFACTS/deliver.json`；运行之间只通过主 Agent 答复各自人工任务协调，不直接发消息。此流程不改变成员需求运行的检查与合并路径。

测试在 `test/plugins/composer/`，用临时 Git 仓库及假的 coda-agent、gh 验证，不发真实 PR 或部署。网关条件用同版本 FEEL 求值真实 BPMN（脚本输出先照引擎把 `"true"` / `"false"` 转为布尔值），覆盖块不开 PR、squash 成一个提交与以合并提交快进合进需求分支、试合并冲突、重跑不重复合入、放弃以出错结束，需求运行的建需求分支与沿用、进行中的三种答复、PR 正文、检查复用、各处失败回到进行中与合并方式；check 包仅校验流程方言，这些测试不运行完整 BPMN 引擎。设备验收段测试覆盖有无设备时的分流、占用范围、退出和重入路径。
